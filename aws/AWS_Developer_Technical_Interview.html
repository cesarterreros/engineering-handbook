1) How to use this guide

Suggested plan (2–4 weeks):
  1. Week 1: IAM/security, VPC/networking fundamentals, S3 + KMS, Lambda basics.
  2. Week 2: event-driven (SQS/SNS/EventBridge), API Gateway, DynamoDB, RDS basics, observability.
  3. Week 3: containers (ECS/EKS), CI/CD + IaC, reliability/DR patterns.
  4. Week 4: AI/GenAI integration (Bedrock + RAG + Guardrails), system design drills, mock interviews.

As a Senior AWS Developer, interviewers expect you to:

  • Translate business requirements into AWS designs with security, cost, and operational excellence.
  • Demonstrate strong failure-mode thinking (timeouts, retries, idempotency, backpressure).
  • Ship software with repeatable delivery (IaC, CI/CD, testing, observability).
  • Handle data + events correctly (ordering, duplication, schema evolution).
  • Integrate AI safely (privacy, guardrails, PII redaction, prompt-injection mitigations).

2) Core senior interview expectations

Signals of seniority

  • Principle of least privilege IAM; separation of duties; account strategy.
  • Designing for retries, DLQs, idempotency, rate limits, and partial failures.
  • Good defaults: encryption everywhere, private networking, logging, alarms, dashboards.
  • Can explain tradeoffs with numbers (RTO/RPO, p99 latency, throughput, cost drivers).
  • Understands AWS service limits and mitigations (quotas, partitioning, sharding).

Common failure points

  • Over-trusting “at-least-once” delivery (SQS/Lambda) → duplicate processing bugs.
  • No backpressure controls → cascading failures and retry storms.
  • Hard-coded config/secrets; no rotation; improper KMS key policies.
  • Poor network design (no endpoints, open SGs, NAT cost surprises).
  • Observability gaps (no correlation IDs, missing traces, no SLOs).

Senior answer format (use in interviews)

  1. Clarify requirements: SLA/SLO, traffic, data sensitivity, compliance, latency, regions.
  2. Propose a baseline architecture (AWS services) + explain why.
  3. Call out failure modes: retries, DLQs, circuit breakers, timeouts, quotas.
  4. Security: IAM, encryption, network isolation, logging/auditing.
  5. Operations: monitoring, alerts, runbooks, deployment strategy, rollback.
  6. Cost: main cost drivers and levers.

3) IAM & Security Engineering

IAM fundamentals you must nail

  • Policy evaluation logic: explicit deny > allow; SCPs and permissions boundaries can limit effective permissions.
  • Roles vs Users: prefer roles + short-lived credentials (STS). Avoid long-lived keys.
  • Trust policy vs permission policy: trust = who can assume; permission = what they can do.
  • Resource policies (S3, KMS, SNS, SQS, API Gateway, Lambda) vs identity policies.
  • ABAC: using tags + conditions to scale access controls.

Org-level controls

  • AWS Organizations + SCPs: enforce guardrails (deny creating internet gateways, deny disabling CloudTrail, etc.).
  • Centralized logging: org trail + centralized S3 bucket, CloudWatch log aggregation, security account pattern.
  • IAM Access Analyzer: find public/resource-sharing exposures.

Encryption & KMS

  • Envelope encryption: data key per object/record; master key in KMS.
  • KMS key policy is authoritative; IAM policy alone doesn’t grant if key policy denies.
  • Understand grant usage for AWS services (e.g., EBS, S3 SSE-KMS).
  • Rotation strategy: enable key rotation (where applicable), plan re-encryption for long-lived data.

Secrets

  • Secrets Manager for rotation; SSM Parameter Store for config (secure strings if needed).
  • Don’t log secrets; ensure redaction in app logs.
  • Prefer IAM auth (RDS IAM auth, Cognito/OIDC, SigV4) over static secrets when possible.

Security logging

  • CloudTrail (management + data events where necessary).
  • VPC Flow Logs, ALB/NLB logs, S3 access logs (or CloudTrail data events).
  • GuardDuty, Security Hub, Detective (know what they are used for).

Interview-ready examples

AWS CLI: create a least-privileged role for Lambda

# Trust policy (lambda can assume role)
cat > trust.json << 'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Principal": { "Service": "lambda.amazonaws.com" }, "Action": "sts:AssumeRole" }
  ]
}
EOF

aws iam create-role --role-name MyLambdaRole --assume-role-policy-document file://trust.json

# Attach AWS managed basic execution (logs). In real cases, prefer custom policies as well.
aws iam attach-role-policy --role-name MyLambdaRole --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole

4) Networking (VPC) & Edge

VPC essentials

  • Subnets: public vs private is about routing (IGW route).
  • Route tables, IGW, NAT Gateway (cost + AZ scope), egress-only IGW (IPv6).
  • Security Groups (stateful) vs NACLs (stateless).
  • VPC Endpoints: Interface (PrivateLink) vs Gateway (S3/DynamoDB). Big impact on security and NAT costs.
  • DNS: Route 53, private hosted zones, resolver endpoints for hybrid.

Load balancing & TLS

  • ALB: L7 HTTP/HTTPS, path-based routing, WAF integration, auth.
  • NLB: L4 TCP/UDP, static IP, high performance; TLS termination possible.
  • ACM certs; mTLS patterns when needed; consider AWS Private CA for internal.

Edge & protection

  • CloudFront for caching/edge; origin access control for S3 origins.
  • AWS WAF for L7 filtering; rate-based rules; managed rule groups.
  • AWS Shield (Standard/Advanced) for DDoS protection.

CLI: create VPC endpoint for S3 (Gateway endpoint)

aws ec2 create-vpc-endpoint \
  --vpc-id vpc-1234567890abcdef0 \
  --service-name com.amazonaws.us-east-1.s3 \
  --vpc-endpoint-type Gateway \
  --route-table-ids rtb-aaaabbbbccccdddd

Senior interview networking prompts

  • How do you keep Lambdas private while accessing S3/DynamoDB/Secrets Manager?
  • How would you design multi-AZ ingress and egress? Where does NAT cost appear?
  • How do you do zero-trust between microservices (mTLS, IAM auth, private endpoints)?

5) Compute: EC2, Auto Scaling, Lambda

EC2 + ASG

  • Launch Templates, Mixed Instances, Spot + On-Demand blending.
  • Lifecycle hooks for bootstrap/drain; instance refresh for rolling updates.
  • Placement groups for low-latency clusters when needed.

Lambda (advanced)

  • Concurrency: reserved, provisioned; understand throttling.
  • Cold starts: mitigations (provisioned concurrency, smaller packages, avoid VPC where unnecessary).
  • Timeouts: align Lambda timeout with upstream timeouts; prevent retries from exceeding idempotency window.
  • Retries: async invocations retry; event source mapping retry semantics differ (SQS vs DynamoDB streams vs Kinesis).
  • Destinations (success/failure) and DLQs (SQS/SNS).

Python: Lambda idempotency (simple DynamoDB-based pattern)

import os, time, json
import boto3
from botocore.exceptions import ClientError

ddb = boto3.client("dynamodb")
TABLE = os.environ["IDEMPOTENCY_TABLE"]

def handler(event, context):
    # Use a stable request key (messageId, orderId, etc.)
    key = event.get("idempotencyKey") or event["Records"][0]["messageId"]

    ttl = int(time.time()) + 3600
    try:
        ddb.put_item(
            TableName=TABLE,
            Item={"pk": {"S": key}, "expiresAt": {"N": str(ttl)}},
            ConditionExpression="attribute_not_exists(pk)"
        )
    except ClientError as e:
        if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
            return {"statusCode": 200, "body": "Duplicate ignored"}
        raise

    # Do the real work
    return {"statusCode": 200, "body": json.dumps({"ok": True})}

6) Serverless & Event-driven Systems

Core concepts

  • At-least-once delivery is the default: duplicates happen. Make consumers idempotent.
  • Ordering: SQS Standard is best-effort order; FIFO provides ordering within message group.
  • Backpressure: control concurrency (Lambda reserved concurrency; SQS batch size; EventBridge retry policies).
  • Schema evolution: version your events; avoid breaking changes; consider schema registry patterns.

SQS deep dive

  • Visibility timeout must exceed max processing time; extend visibility if needed.
  • DLQ redrive: choose maxReceiveCount; capture failure reasons.
  • FIFO: deduplication window and message group scaling constraints (design message groups carefully).

CLI: Create SQS queue + DLQ and redrive policy

# Create DLQ
DLQ_URL=$(aws sqs create-queue --queue-name orders-dlq --query 'QueueUrl' --output text)
DLQ_ARN=$(aws sqs get-queue-attributes --queue-url "$DLQ_URL" --attribute-names QueueArn --query 'Attributes.QueueArn' --output text)

# Create main queue with redrive policy
aws sqs create-queue --queue-name orders-queue \
  --attributes "RedrivePolicy={\"deadLetterTargetArn\":\"$DLQ_ARN\",\"maxReceiveCount\":\"5\"}"

EventBridge

  • Event routing with rules (pattern matching); decouple producers/consumers.
  • Retries + DLQ for targets; archive/replay (if enabled) for recovery/testing patterns.
  • Great for domain events and integrating SaaS/AWS services.

Step Functions

  • Standard vs Express: Standard for long-running/durable workflows; Express for high-throughput short workflows.
  • Use retries with exponential backoff + jitter, catch blocks, compensation (saga).
  • Human-in-the-loop patterns via callbacks/task tokens when required.

Design pattern: Saga (orchestration)

Example: order creation → payment → inventory → shipping with compensation when later steps fail. Step Functions coordinates; each microservice is independently deployable.

7) Containers: ECS, EKS, Fargate

ECS (Fargate) vs EKS

ECS/Fargate

  • Lower operational overhead; strong AWS integration.
  • Great for most microservices and batch-like workloads.
  • Use Service Auto Scaling + ALB/NLB; IAM task roles.

EKS (Kubernetes)

  • More flexibility/ecosystem; more ops complexity.
  • Requires strong cluster hygiene: upgrades, CNI, autoscaling, policies.
  • Use IRSA (IAM Roles for Service Accounts) for least privilege.

Container security

  • Image scanning (ECR scanning + CI scanning).
  • Runtime permissions: task role/IRSA; drop linux capabilities; read-only fs where possible.
  • Secrets injection: Secrets Manager/SSM; avoid baking into images.

AWS CLI: push image to ECR (outline)

aws ecr create-repository --repository-name myapp

aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin <accountId>.dkr.ecr.us-east-1.amazonaws.com

docker build -t myapp:1 .
docker tag myapp:1 <accountId>.dkr.ecr.us-east-1.amazonaws.com/myapp:1
docker push <accountId>.dkr.ecr.us-east-1.amazonaws.com/myapp:1

8) Storage: S3, EBS, EFS, FSx

S3 (must-know)

  • Consistency: strong read-after-write consistency for PUT/DELETE (modern S3 behavior).
  • Security: Block Public Access, bucket policies, OAC with CloudFront, access points.
  • Encryption: SSE-S3 vs SSE-KMS; KMS policies and cost implications.
  • Lifecycle: transition to IA/Glacier; expiration; storage class analysis.
  • Events: S3 notifications to SQS/SNS/Lambda; beware of recursion loops.

CLI: enable default SSE-KMS on a bucket

aws s3api put-bucket-encryption --bucket my-bucket --server-side-encryption-configuration '{
  "Rules": [{
    "ApplyServerSideEncryptionByDefault": {
      "SSEAlgorithm": "aws:kms",
      "KMSMasterKeyID": "alias/my-key"
    }
  }]
}'

EBS/EFS/FSx quick guidance

  • EBS: block storage; snapshots; gp3 vs io2 tradeoffs; encryption by default.
  • EFS: shared NFS; great for shared workloads; performance modes; mount targets per AZ.
  • FSx: specialized (Windows, Lustre, NetApp ONTAP) when you need those semantics.

9) Databases & Caching

DynamoDB

  • Partition key design drives scalability; avoid hot partitions.
  • LSI/GSIs: understand access patterns; projection; write costs.
  • Conditional writes for idempotency; transactions where needed (cost/latency tradeoffs).
  • DynamoDB Streams + Lambda for CDC/eventing patterns.

Python: conditional write (optimistic locking-ish)

import boto3
ddb = boto3.client("dynamodb")

ddb.update_item(
    TableName="Orders",
    Key={"pk": {"S": "order#123"}, "sk": {"S": "meta"}},
    UpdateExpression="SET #s = :new, version = version + :one",
    ConditionExpression="version = :expected",
    ExpressionAttributeNames={"#s": "status"},
    ExpressionAttributeValues={
        ":new": {"S": "PAID"},
        ":expected": {"N": "3"},
        ":one": {"N": "1"}
    }
)

RDS / Aurora

  • Connection management: poolers, RDS Proxy for Lambda, max connections planning.
  • Backups + PITR, read replicas, Multi-AZ (HA) vs read scaling (replicas).
  • Aurora: reader endpoint, failover behavior; understand quorum storage conceptually.

ElastiCache (Redis/Memcached)

  • Cache-aside vs write-through; TTLs; stampede protection.
  • Redis for rate limiting, sessions, pub/sub (careful), distributed locks (careful).

OpenSearch

  • Use for search/analytics; index design, shard sizing, ingestion pipelines.
  • Security: fine-grained access control, VPC deployment.

11) Observability: CloudWatch, X-Ray, OpenTelemetry

What “good” looks like

  • Metrics: RED (Rate, Errors, Duration) for APIs; USE for resources (Utilization, Saturation, Errors).
  • Logs: structured JSON logs with correlation IDs; PII redaction.
  • Tracing: distributed trace across services; propagate trace/correlation headers.
  • Alarms: symptom-based alarms (error rate, latency, saturation) + business KPIs.

CloudWatch specifics

  • Log groups retention policies; metric filters for critical patterns.
  • Dashboards per service and per customer journey.
  • Synthetics canaries for external checks.

CDK

13) CI/CD & Release Engineering

Build pipeline basics

  • Build, unit tests, security scans (SAST, dependency, container), package, deploy.
  • Promote artifacts (immutable) across environments; avoid rebuilding for prod.

Deployment strategies

  • Blue/Green (safe rollbacks), Canary, Rolling.
  • Lambda: aliases + weighted traffic shifting (CodeDeploy) for canary deployments.
  • Containers: ECS blue/green with CodeDeploy; EKS progressive delivery with Argo Rollouts (if used).

Policy as code

  • Check IAM wildcards, public S3, open SGs, missing encryption, missing retention.
  • Tools: OPA/Conftest, Checkov, cdk-nag, tfsec (depending on IaC choice).

14) Reliability, DR, Multi-Region

Key terms

  • RTO: time to restore service.
  • RPO: acceptable data loss window.
  • Multi-AZ vs Multi-Region: HA vs regional resilience.

Common DR strategies

  • Backup & Restore: lowest cost, highest RTO.
  • Pilot Light: minimal core running, scale during failover.
  • Warm Standby: scaled-down full environment.
  • Active/Active: highest complexity/cost, best resilience.

Resilient app practices

  • Timeouts everywhere; bounded retries; jitter; circuit breakers.
  • Bulkheads: isolate dependencies, queues, concurrency pools.
  • Graceful degradation: cached/stale reads, reduced features.
  • Runbooks + game days/chaos testing where feasible.

15) Performance & Cost Optimization

Cost drivers to mention in interviews

  • NAT Gateway data processing + hours (often a surprise).
  • CloudWatch logs ingestion and retention.
  • S3 requests and data retrieval, especially Glacier classes.
  • Lambda duration + provisioned concurrency.
  • Data transfer across AZ/Region; CloudFront egress optimization.
  • RDS/Aurora sizing, IOPS, and over-provisioned replicas.

Performance levers

  • Caching: CloudFront, API caching (where applicable), Redis.
  • Async processing with queues; batch where safe.
  • Use VPC endpoints; reduce network hops.
  • Choose the right database for access patterns.

16) AI/GenAI on AWS: Bedrock, SageMaker, and Integration Patterns

Senior expectation: You must show you can integrate GenAI safely: privacy, least privilege, auditability, prompt-injection mitigations, PII redaction, and grounding (RAG).

Service map

  • Amazon Bedrock: managed foundation model (FM) access + tooling (agents, knowledge bases, guardrails).
  • Guardrails for Amazon Bedrock: centralized safety controls (content filters, PII filters, topic restrictions, grounding checks).
  • Knowledge Bases for Amazon Bedrock: managed RAG (ingest docs, chunk/embed, retrieve).
  • Amazon SageMaker: build/train/deploy ML models; MLOps, feature store patterns, notebooks, endpoints.
  • Amazon OpenSearch / Aurora pgvector / DynamoDB (as metadata): possible components in custom RAG stacks.
  • EventBridge / Step Functions: orchestration of AI workflows and tool-calling pipelines.

GenAI architectural patterns (interview-grade)

A) RAG (Retrieval Augmented Generation)

Goal: reduce hallucinations by grounding answers in your documents.

  • Ingest documents (S3, Confluence, SharePoint connectors depending on stack).
  • Chunking strategy matters (structure-aware chunking beats naive fixed-size for docs).
  • Embed chunks; store vectors; at query-time retrieve top-k, then generate with citations.
  • Add guardrails and grounding checks.

B) Tool use / Agents

Goal: model decides when to call tools (APIs) to complete tasks.

  • Define actions with least privilege (IAM role for agent/tool execution).
  • Constrain tools: allowlist operations; validate inputs; implement safe retries and timeouts.
  • Log every tool invocation (CloudTrail, app logs) for audit.

C) Async AI pipelines

  • Queue requests via SQS; worker does Bedrock invocation; store results in DynamoDB/S3.
  • Use Step Functions for multi-step: classify → retrieve → generate → validate → store → notify.

GenAI security & safety checklist

  • Data boundaries: do not send secrets/PII unless required; minimize prompt content.
  • PII redaction: before sending to model; also filter output.
  • Prompt injection defenses:
    • Treat retrieved docs as untrusted input; separate system instructions from context.
    • Use allowlisted tools; never let model choose arbitrary URLs or credentials.
    • Implement grounding requirements (“answer only from provided sources”).
  • Guardrails: enforce topic restrictions, harmful content filters, and sensitive info filters.
  • Audit: log prompts/outputs carefully (redact); keep trace IDs and tool-call logs.
  • Networking: prefer private connectivity where possible; restrict egress.

Python: Bedrock invocation (runtime) pattern

import json
import boto3

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

# Example uses a generic "messages" style payload used by some FMs.
# Exact schema depends on the model provider; always follow the model's request format.
model_id = "anthropic.claude-3-5-sonnet-20240620-v1:0"  # example; choose what your account has access to

payload = {
  "messages": [
    {"role": "user", "content": [{"type": "text", "text": "Explain idempotency for SQS consumers with an example."}]}
  ],
  "max_tokens": 400
}

resp = bedrock.invoke_model(
    modelId=model_id,
    contentType="application/json",
    accept="application/json",
    body=json.dumps(payload)
)

body = json.loads(resp["body"].read())
print(body)

Bedrock Knowledge Bases (managed RAG) — what to explain

  • Create knowledge base; connect data source (often S3); run ingestion.
  • At query time: retrieve relevant chunks; generate answer grounded in sources.
  • Operational concerns: ingestion schedule, document versioning, access control to source docs.

Python: Knowledge Base creation (pattern consistent with AWS blog examples)

import boto3

bedrock_agent = boto3.client("bedrock-agent", region_name="us-west-2")

kb = bedrock_agent.create_knowledge_base(
    name="my-managed-kb",
    description="Product docs",
    roleArn="arn:aws:iam::123456789012:role/BedrockKBRole",
    knowledgeBaseConfiguration={
        "type": "MANAGED",
        "managedKnowledgeBaseConfiguration": {
            "embeddingModelType": "MANAGED"
        }
    }
)

kb_id = kb["knowledgeBase"]["knowledgeBaseId"]
print("KB:", kb_id)

ds = bedrock_agent.create_data_source(
    knowledgeBaseId=kb_id,
    name="my-s3-docs",
    dataSourceConfiguration={
        "type": "S3",
        "s3Configuration": {
            "bucketArn": "arn:aws:s3:::my-docs-bucket",
            "inclusionPrefixes": ["documents/"]
        }
    }
)

bedrock_agent.start_ingestion_job(
    knowledgeBaseId=kb_id,
    dataSourceId=ds["dataSource"]["dataSourceId"]
)
print("Ingestion started")

Guardrails for Bedrock — what to explain

  • Central policy layer: harmful content filters, denied topics, word filters, sensitive info (PII) filters.
  • Apply consistently across models; prefer “defense in depth” (guardrails + app validation + least privilege).
  • Use to reduce risk of leaking PII/secrets and to enforce policy constraints.

Interview scenarios with AI

  1. Customer support summarizer: redact PII, store transcript in S3, summarize via Bedrock, keep audit logs.
  2. Internal doc assistant: RAG with Knowledge Bases; per-document ACL enforcement; citations; guardrails.
  3. Agentic deploy helper: tool calls to CI/CD APIs; strict allowlists; approvals; full audit trail.

17) System Design prompts & answer frameworks

Prompt 1: “Design an order processing platform (10k orders/min) with exactly-once business effects”

  • API Gateway + Lambda/ECS for ingest; validate and write to DynamoDB (idempotency key).
  • Emit domain event to EventBridge; route to SQS per downstream bounded context.
  • Consumers use conditional writes / dedupe store; DLQs for poison messages.
  • Step Functions for long workflows; compensations for failures.
  • Observability: trace IDs, dashboards, alarms, DLQ depth alerts.

Prompt 2: “Design a GenAI doc assistant for internal policies”

  • Docs in S3, access controlled; ingest into Bedrock Knowledge Base.

19) Senior-level question bank (with what interviewers want)

IAM/Security

  • How do SCPs, permissions boundaries, and IAM policies interact?
    They want: layered evaluation + explicit deny precedence; boundaries limit maximum permissions.
  • Explain KMS key policy vs IAM policy; why does access fail even with IAM allow?
    They want: key policy can block; both must permit; grants used by services.
  • How do you prevent data exfiltration from a VPC?
    They want: endpoints, egress controls, NACL/SG, DNS controls, proxies, logging, WAF.

Serverless/Event-driven

  • SQS visibility timeout vs Lambda timeout—how do you set them?
    They want: visibility > max processing; handle extension; avoid duplicate inflight.
  • How do you guarantee “exactly once” effects?
    They want: idempotency keys + conditional writes/transactions + outbox/CDC patterns.

Databases

  • DynamoDB hot partition: how do you detect and fix?
    They want: metrics (throttles, consumed capacity), key redesign, sharding, write spreading.
  • Lambda to RDS: what goes wrong at scale?
    They want: connection storms; use RDS Proxy, pooling, limit concurrency.

Observability

  • What alarms would you set for an API?
    They want: 5xx rate, p95/p99 latency, saturation, dependency errors, DLQ depth.

AI/GenAI

  • How do you reduce hallucinations?
    They want: RAG, grounding checks, constrained answers, evals, citations.
  • How do you mitigate prompt injection?
    They want: treat retrieved text as untrusted, tool allowlists, guardrails, isolation, validation.
  • Where do you store prompts and outputs?
    They want: minimize retention; redact; encrypt; strict access; audit trails.

sqs = session.client("sqs")
resp = sqs.list_queues()
