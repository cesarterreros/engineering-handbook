Technical Interview Cheat Sheet

.NET / ASP.NET Core · EF Core · PostgreSQL — condensed high-value notes (2024/2025)

.NET / ASP.NET Core

Unmanaged Resources

Resources the GC doesn't track: file handles, DB connections, sockets, native memory, unmanaged pointers.

  • Implement IDisposable / IAsyncDisposable; free them in Dispose().
  • Use using / await using for deterministic cleanup.
  • Dispose pattern: Dispose(bool disposing) + GC.SuppressFinalize(this).
  • A finalizer (~Class()) is a safety net only — costs an extra GC cycle.
  • Prefer SafeHandle over raw IntPtr for native handles.

async / await

  • Frees the thread during I/O waits — scalability, not raw speed.
  • Async all the way down; never .Result/.Wait() → deadlocks.
  • Return Task/Task<T>; use ValueTask for hot, often-sync paths.
  • async void only for event handlers (exceptions can't be caught).
  • ConfigureAwait(false) in libraries (no SyncContext in ASP.NET Core anyway).
  • Parallelize independent work: await Task.WhenAll(t1, t2).
  • Support CancellationToken for cancellation/timeouts.

Middleware vs Action Filters

MiddlewareAction Filter
Whole HTTP pipelineOnly MVC/API actions
Runs before routing decidedAfter model binding
No MVC context (model state)Access to args, ModelState, result
Cross-cutting: auth, logging, CORSAction-specific: validation, caching

Order: Middleware → Routing → Auth → Filters (Authorization→Resource→Action→Exception→Result).

  • Middleware pipeline runs for ALL requests — app-level concerns: logging, HTTPS redirection, performance profiling, exception handling.
  • Filter pipeline is a subset of the middleware pipeline, executing inside the Endpoint Middleware.
  • Filters run only for requests that reach the Endpoint Middleware (a matched action).
  • Filters handle MVC-specific work: ViewData, ViewBag, ModelState, action result.

Global Exception Handling

  • Modern (.NET 8+): IExceptionHandler + app.UseExceptionHandler().
  • app.UseExceptionHandler("/error") or lambda handler.
  • Return RFC 9457 ProblemDetails (AddProblemDetails()).
  • Alternatives: exception-handling middleware, [ExceptionFilter] (MVC-only).
  • Use UseDeveloperExceptionPage only in Development.
public class GlobalHandler : IExceptionHandler {
  public async ValueTask<bool> TryHandleAsync(
    HttpContext c, Exception e, CancellationToken t){
    await c.Response.WriteAsJsonAsync(
      new ProblemDetails{ Title = e.Message }, t);
    return true; } }

  • Build HTTP services only — no support for MVC Views.
  • Endpoint Filters instead of MVC filters.
  • Reduce memory allocations per request.

Captive Dependencies

A longer-lived service captures a shorter-lived one, extending its lifetime unintentionally.

  • Classic bug: Singleton injects Scoped (e.g. DbContext) → stale/thread-unsafe.
  • Rule: never inject a shorter lifetime into a longer one.
  • Fixes: inject IServiceScopeFactory and create a scope, or use a factory.
  • Validated at startup by default in Dev (ValidateScopes).

Lifetimes: Transient (each request), Scoped (per HTTP request), Singleton (app lifetime).

JWT

JSON Web Token = header.payload.signature (Base64Url), stateless bearer token.

  • Header: alg (HS256/RS256), typ. Payload: claims (sub, exp, iss, aud, roles).
  • Signature: verifies integrity — not encrypted, don't store secrets.
  • Always validate issuer, audience, expiry, signature.
  • Short-lived access token + long-lived refresh token; revocation is hard (stateless).
  • Prefer RS256 (asymmetric) for multi-service; store client-side in httpOnly cookie or memory.
builder.Services.AddAuthentication().AddJwtBearer(o =>
  o.TokenValidationParameters = new(){
    ValidateIssuer=true, ValidateAudience=true,
    ValidateLifetime=true, ValidateIssuerSigningKey=true });

XSS · CSRF · CORS · SQL Injection

XSS Cross Site Scripting — Inject malicious script into page. Fix: encode/escape output, CSP header, avoid innerHTML, Razor auto-encodes.

CSRF Cross Site Request Forgery — Forged request using victim's cookies. Fix: anti-forgery token ([ValidateAntiForgeryToken]), SameSite cookies, don't use cookies for pure APIs (use bearer).

CORS Cross Origin Resource Sharing — Browser same-origin policy control (a defense, not an attack). Config: AddCors + UseCors; allow specific origins, avoid AllowAnyOrigin+credentials.

SQLi Injected SQL via input. Fix: parameterized queries / EF Core (never string concat), least-privilege DB user, validate input.

  • Eager = predictable, best default. Lazy convenient but hides N+1.
  • AsSplitQuery() avoids cartesian explosion on multiple Includes.
  • Read-only? add AsNoTracking() for speed.

The N+1 Problem

1 query for the list + N queries for each item's related data.

// BAD: lazy loading in a loop -> 1 + N
foreach (var o in ctx.Orders)
  Console.Write(o.Customer.Name);
// GOOD: 1 query
ctx.Orders.Include(o => o.Customer)
  • Cause: lazy loading or accessing navs per row.
  • Fix: Include, projection (Select), or split query.
  • Detect: EF Core logs a warning; inspect generated SQL.

Optimistic Concurrency

Assume conflicts are rare; detect on save instead of locking.

  • Add concurrency token: [Timestamp] byte[] RowVersion or .IsConcurrencyToken().
  • PostgreSQL: use xmin system column → .UseXminAsConcurrencyToken().
  • UPDATE includes token in WHERE; 0 rows → DbUpdateConcurrencyException.
  • Resolve: reload DB values, merge, retry (client-wins / store-wins).

Pessimistic = DB locks (FOR UPDATE); EF has no first-class support.

Global Query Filters

Predicate auto-applied to every query for an entity (LINQ WHERE).

modelBuilder.Entity<Post>()
  .HasQueryFilter(p => !p.IsDeleted
     && p.TenantId == _tenantId);
  • Great for soft delete and multitenancy.
  • Bypass with .IgnoreQueryFilters().
  • .NET 10: named filters allow multiple/selective bypass.
  • Applies to root; watch required navigations & Includes.

Migrations

Version-controlled, incremental schema changes from your model.

dotnet ef migrations add Init
dotnet ef database update
dotnet ef migrations remove   // undo last (if not applied)
dotnet ef migrations script   // SQL for prod
  • Each migration = Up() / Down() + model snapshot.
  • Prod: generate idempotent SQL scripts, review before applying.
  • Never edit applied migrations; add a new one.
  • __EFMigrationsHistory table tracks what's applied.

  • Shared schema: enforce with EF global query filter on TenantId.
  • Postgres Row-Level Security (RLS) enforces at DB level regardless of app bugs.
  • Index on TenantId; beware cross-tenant leaks & noisy neighbors.

Row-Level Security (RLS)

Attach policies that auto-filter rows by who is querying. With a session setting like current_setting('app.current_tenant'), enforce tenant isolation at the DB level — no need to add WHERE tenant_id = ? to every query.

CREATE POLICY tenant_isolation_policy ON your_table
  FOR ALL
  USING (tenant_id =
    current_setting('app.current_tenant')::bigint);

⇒ For any SELECT/UPDATE/DELETE, only rows where tenant_id matches the session's app.current_tenant.

In your app, before querying on that connection:

SET LOCAL app.current_tenant = '123';
  • SET LOCAL applies only for the current transaction (ideal for web requests).
  • All later queries on that connection auto-see only tenant 123's rows.
  • With pooled connections, reset per transaction — use SET LOCAL inside a txn, not plain SET.
  • Must also ENABLE ROW LEVEL SECURITY on the table for policies to apply.

SQL Constraints

  • PRIMARY KEY unique + not null, identifies row.
  • FOREIGN KEY referential integrity (ON DELETE CASCADE/SET NULL/RESTRICT).
  • UNIQUE no duplicate values (allows one NULL in PG).
  • NOT NULL value required.
  • CHECK custom boolean rule, e.g. price > 0.
  • DEFAULT value when none supplied.
  • EXCLUDE (PG-specific) e.g. no overlapping ranges.

Clustered vs Non-Clustered Index

  • Clustered: table rows physically ordered by key; one per table.
  • Non-clustered: separate structure with pointers; many allowed.
  • PostgreSQL has no permanent clustered index — heap storage. CLUSTER table USING idx is a one-time reorder (not maintained).
  • All PG indexes are effectively "non-clustered" (B-tree by default; also GIN, GiST, BRIN, Hash).
  • PK creates a unique B-tree index, not a clustered store.

Relationships (Cardinality)

  • 1-to-1: FK with UNIQUE on child (or shared PK). E.g. User–Profile.
  • 1-to-many: FK on the "many" side. E.g. Customer–Orders.
  • many-to-many: junction/join table with two FKs (composite PK). E.g. Student–Course → Enrollment.

EF Core: 1-1 HasOne/WithOne, 1-m HasOne/WithMany, m-m auto join entity (EF5+) HasMany/WithMany.

Isolation Levels

LevelDirtyNon-repeatPhantom
Read Uncommitted—*YesYes
Read CommittedNoYesYes
Repeatable ReadNoNoNo*
SerializableNoNoNo
  • PG default = Read Committed. *PG treats Read Uncommitted as Read Committed (no dirty reads ever).
  • PG uses MVCC (snapshots), not read locks.
  • PG Repeatable Read also prevents phantoms; may throw serialization errors → retry.
  • Serializable = strongest (SSI); may abort txns needing retry.

Anomalies: Dirty read (uncommitted data), Non-repeatable read (row changed on re-read), Phantom (new rows match on re-query).

RabbitMQ (for .NET developers)

Core Model (AMQP 0-9-1)

Producer → Exchange → (binding) → Queue → Consumer. Producers never publish directly to a queue.

  • Exchange routes messages using a routing key + bindings.
  • Queue = durable buffer holding messages until acked.
  • Binding = rule linking exchange → queue.
  • Channel = lightweight virtual connection; do work on channels, not raw TCP connections.
  • Vhost = logical isolation (separate exchanges/queues/permissions).

Exchange Types

TypeRoutingUse
directExact routing-key matchPoint-to-point, log levels
topicPattern *=1 word #=0+ wordsCategory routing order.*.eu
fanoutBroadcast to all bound queues (ignores key)Pub/sub, cache invalidation
headersMatch on header args (not key)Complex multi-attr routing

Default (nameless "") exchange is a direct exchange; routing key = queue name.

Reliability: Acks & Confirms

  • Consumer ack: use manual ack (autoAck:false) — ack after successful processing.
  • BasicAckAsync (success), BasicNackAsync/BasicRejectAsync with requeue flag.
  • Publisher confirms: broker acks the producer — the only safe way to know a message was persisted.
  • Durable queue + persistent message (Persistent=true) survive broker restart. Both required.
  • Gotcha: durable queue with non-persistent messages still loses messages on restart.

.NET Client (v7+, async)

NuGet RabbitMQ.Client 7.x is fully async (CreateConnectionAsync, BasicPublishAsync).

var factory = new ConnectionFactory { HostName = "localhost" };
await using var conn = await factory.CreateConnectionAsync();
await using var ch = await conn.CreateChannelAsync();
await ch.QueueDeclareAsync("orders", durable:true,
    exclusive:false, autoDelete:false);
var body = JsonSerializer.SerializeToUtf8Bytes(order);
var props = new BasicProperties { Persistent = true };
await ch.BasicPublishAsync("", "orders",
    mandatory:false, props, body);
  • Reuse ONE connection; create a channel per thread/consumer (not thread-safe to share).
  • Consumer: AsyncEventingBasicConsumer + BasicConsumeAsync.

Throughput & Fair Dispatch

  • Prefetch (BasicQosAsync(0, prefetchCount, false)) caps unacked messages per consumer → fair dispatch, prevents one worker hoarding.
  • Low prefetch (1–10) = even load; high prefetch = more throughput but risk of imbalance.
  • Scale out with competing consumers on the same queue (work queue pattern).
  • Order is preserved per queue with a single consumer only.

DLX, TTL & Retries

  • Dead Letter Exchange: messages rejected/nacked (requeue=false), expired (TTL), or over max-length go to the DLX.
  • Set via args: x-dead-letter-exchange, x-message-ttl, x-max-length.
  • Retry pattern: DLX → retry queue with TTL → dead-letters back to main queue (delayed retry). No native delay without the delayed-message plugin.
  • Track x-death header to cap retry attempts → park in a parking/poison queue.
  • Avoid blind requeue:true on failures → infinite hot-loop.

Quorum Queues (default choice)

  • Quorum queues (Raft-based) are the modern default for HA — replicated across nodes, consistent, durable.
  • Classic mirrored queues are deprecated/removed (RabbitMQ 4.x). Use quorum instead.
  • Support poison-message handling via x-delivery-limit.
  • Streams: append-only log (replayable, high-throughput, Kafka-like) for large fan-out / replay scenarios.

RabbitMQ vs Kafka

Pick RabbitMQ for flexible routing, work queues, per-message ack; Kafka for replay & huge throughput.

Patterns & Best Practices

  • Ensure idempotent consumers — delivery is at-least-once; duplicates happen (dedupe by message id).
  • Use the transactional outbox to publish reliably with a DB commit (avoid dual-write loss).
  • Set MessageId, CorrelationId, ContentType on BasicProperties.
  • RPC: ReplyTo + CorrelationId, use built-in amq.rabbitmq.reply-to (direct reply-to).
  • Prefer higher-level frameworks: MassTransit or EasyNetQ for retries, sagas, serialization.
  • Handle reconnects: enable AutomaticRecoveryEnabled (on by default) + topology recovery.
