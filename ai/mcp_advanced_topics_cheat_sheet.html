MCP Advanced Topics Cheat Sheet

Practical reference for advanced Model Context Protocol behavior, transport constraints, and client/server communication patterns. Verify details against the current MCP specification and SDK behavior before production use.

1. Sampling

Sampling lets an MCP server request text generation through the connected MCP client instead of calling an LLM directly.

Why use it?

  • The server does not need an LLM API key.
  • The server avoids implementing provider-specific SDK integration.
  • The client—not the server—pays for token usage.
  • It is especially useful for public MCP servers, preventing the server owner from paying for every user's generation request.
  • It shifts LLM authentication, billing, and model access to the client.

Request flow

  1. The server performs its primary task, such as collecting research data.
  2. The server builds a prompt.
  3. The server sends a sampling request to the client.
  4. The client calls its configured language model.
  5. The client returns the generated content.
  6. The server uses that content in its final response.

Server-side pattern

@mcp.tool()
async def summarize(text_to_summarize: str, ctx: Context):
    prompt = f"""
    Please summarize the following text:
    {text_to_summarize}
    """

    result = await ctx.session.create_message(
        messages=[
            SamplingMessage(
                role="user",
                content=TextContent(
                    type="text",
                    text=prompt
                )
            )
        ],
        max_tokens=4000,
        system_prompt="You are a helpful research assistant",
    )

    if result.content.type == "text":
        return result.content.text

    raise ValueError("Sampling failed")

Client-side requirements

The client must provide a sampling callback that invokes its own model:

async def sampling_callback(
    context: RequestContext,
    params: CreateMessageRequestParams
):
    text = await chat(params.messages)

    return CreateMessageResult(
        role="assistant",
        model=model,
        content=TextContent(type="text", text=text),
    )

Register it when creating the session:

async with ClientSession(
    read,
    write,
    sampling_callback=sampling_callback
) as session:
    await session.initialize()

Design principle: MCP sampling provides model access without coupling the server to a specific LLM provider.

2. Logging and Progress

Logging and progress notifications improve the user experience during long-running tool calls. Without them, users may not know whether a tool is still running or has stalled.

Server-side context methods

  • context.info(message) sends a log message.
  • context.report_progress(progress, total) reports execution progress.
@mcp.tool(
    name="research",
    description="Research a given topic"
)
async def research(
    topic: str,
    *,
    context: Context
):
    await context.info("About to do research...")
    await context.report_progress(20, 100)

    sources = await do_research(topic)

    await context.info("Writing report...")
    await context.report_progress(70, 100)

    return await generate_report(sources)

Client-side callbacks

async def logging_callback(
    params: LoggingMessageNotificationParams
):
    print(params.data)
async def print_progress_callback(
    progress: float,
    total: float | None,
    message: str | None
):
    if total is not None:
        percentage = (progress / total) * 100
        print(f"Progress: {progress}/{total} ({percentage:.1f}%)")
    else:
        print(f"Progress: {progress}")

Register logging at session creation and progress when calling a tool:

async with ClientSession(
    read,
    write,
    logging_callback=logging_callback
) as session:
    await session.initialize()

    await session.call_tool(
        name="research",
        arguments={"topic": "MCP"},
        progress_callback=print_progress_callback,
    )

Presentation options

ApplicationPossible implementation
CLIPrint logs and progress to the terminal.
Web applicationWebSockets, Server-Sent Events, or polling.
Desktop applicationProgress bars and status indicators.

These notifications are optional and primarily provide user-experience improvements.

3. Roots and File Access

Roots define the local files and directories that an MCP server is allowed to access.

Problems roots solve

Without roots:

  • The model may not know where a user's file is located.
  • Users would need to provide complete file paths.
  • The server could potentially search too broadly across the filesystem.

With roots:

  1. The user asks to operate on a file, such as biking.mp4.
  2. The client exposes approved directories through list_roots.
  3. The model searches those directories.
  4. The server receives the resolved path.
  5. The tool performs the operation only within the approved boundaries.

Security model

Roots provide boundaries such as:

  • Allow access to Desktop.
  • Deny access to Documents, Downloads, or other directories.
  • Prevent accidental access to sensitive files.
  • Reduce search scope and improve file-discovery performance.

Important implementation warning

The MCP SDK does not automatically enforce root restrictions. The server must validate paths itself.

A typical helper should:

  1. Receive the requested path.
  2. Retrieve the approved roots.
  3. Normalize or resolve the requested path.
  4. Check whether the resolved path is inside an approved root.
  5. Reject the operation if it is outside the allowed boundaries.

Conceptually:

def is_path_allowed(requested_path, allowed_roots):
    resolved_path = requested_path.resolve()

    return any(
        resolved_path.is_relative_to(root.resolve())
        for root in allowed_roots
    )

Always perform this validation before reading, writing, converting, deleting, or executing operations on a file.

Security rule: Never treat a user-provided path as trusted merely because it appears to be inside an allowed directory; resolve it first to prevent traversal attacks.

4. MCP Message Types

MCP communication uses JSON messages defined by the official MCP specification.

Request-result messages

These messages form request/response pairs:

  • Call Tool Request → Call Tool Result
  • List Prompts Request → List Prompts Result
  • Read Resource Request → Read Resource Result
  • Initialize Request → Initialize Result

Notifications

Notifications are one-way messages and do not require a response:

  • Progress notifications.
  • Logging message notifications.
  • Tool-list-changed notifications.
  • Resource-updated notifications.
  • Initialized notifications.
  • Cancellation notifications.

Bidirectional communication

MCP is bidirectional:

  • Clients can send requests to servers.
  • Servers can send requests to clients.
  • Either side can send notifications.
  • Sampling and roots require server-to-client communication.

This distinction is critical when selecting a transport because some HTTP configurations restrict server-initiated communication.

5. STDIO Transport

STDIO is commonly used for local development and testing.

How it works

  • The client launches the MCP server as a subprocess.
  • Client messages are written to the server's stdin.
  • Server messages are written to stdout.
  • Both sides can initiate communication.
  • Client and server must run on the same machine.

Initialization handshake

Every standard MCP connection begins with:

  1. Client sends Initialize Request.
  2. Server returns Initialize Result, including capabilities.
  3. Client sends Initialized Notification.

Only after this handshake should the client call tools, list prompts, or read resources.

Four communication patterns

STDIO supports all four directions:

  • Client → server request.
  • Server → client response.
  • Server → client request.
  • Client → server response.

Best use: Local development, testing, desktop integrations, and full bidirectional MCP functionality.

6. Streamable HTTP Transport

Streamable HTTP enables clients to connect to remotely hosted MCP servers.

Why it is more complex

HTTP naturally supports:

  • Client requests to servers.
  • Server responses to clients.

HTTP does not naturally support:

  • Server-initiated requests.
  • Real-time server-to-client notifications.
  • Responses routed through a persistent client connection.

MCP solves this using Server-Sent Events (SSE).

Stateful connection flow

  1. The client sends an initialization request.
  2. The server returns an initialization result with an mcp-session-id header.
  3. The client sends an initialized notification.
  4. The client opens a long-lived GET/SSE connection.
  5. The server uses the SSE connection for server-to-client messages.
  6. The client uses POST requests for tool calls and other requests.

The session ID must be included in subsequent requests.

Dual-connection model

ConnectionPurpose
Primary SSE connectionServer-initiated requests and progress notifications; remains open.
Tool-specific SSE connectionLogging messages and tool results for an individual call.

Understanding this model is important when debugging remote MCP deployments.

7. stateless_http and json_response

These flags can simplify deployment but disable important MCP capabilities.

stateless_http=True

Stateless mode removes session state and is useful for horizontal scaling behind a load balancer.

Trade-offs:

  • No session IDs.
  • No server-to-client request channel.
  • No sampling.
  • No progress notifications.
  • No subscriptions or resource-update notifications.
  • Initialization is not required.
  • Requests can be handled independently by different server instances.

Use it when:

  • You need simple horizontal scaling.
  • Your tools do not require sampling.
  • You do not need progress or logging streaming.
  • You want to minimize connection coordination.

json_response=True

This disables streaming for POST responses and returns only the final result as plain JSON.

Trade-offs:

  • No intermediate progress messages.
  • No live log messages.
  • No streaming tool output.
  • Only the final tool result is returned.

Use it when:

  • The integration expects ordinary JSON responses.
  • Streaming is unnecessary.
  • Simpler HTTP behavior is more important than live updates.

Development recommendation

Test with the same transport and configuration that will be used in production. A server that works under STDIO may fail after deployment if HTTP settings disable:

  • Sampling.
  • Progress callbacks.
  • Logging.
  • Server-initiated requests.
  • Resource subscriptions.

Core Takeaways

  • Sampling lets servers use the client's model access without owning API keys or token costs.
  • Context-based logging and progress make long-running tools observable.
  • Roots improve file discovery but require explicit server-side path enforcement.
  • MCP is bidirectional, so transport limitations matter.
  • STDIO provides the simplest full-featured communication model.
  • Stateful Streamable HTTP preserves advanced functionality through SSE.
  • stateless_http=True improves scalability but disables server-to-client features.
  • json_response=True simplifies responses but removes streaming behavior.
