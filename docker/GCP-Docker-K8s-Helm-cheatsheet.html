Docker + Kubernetes + Helm on GCP

A dense reference for the common path: build a Docker image → store it in Artifact Registry → deploy it to GKE → expose, scale, secure, observe, and release it with Helm. GKE supports Autopilot (recommended for most production) and Standard (direct node/infrastructure control) modes.

Docker / container workflow Kubernetes, GKE, and Helm workflow

Core concepts

  • Image: immutable package containing application code, runtime, libraries, and metadata.
  • Container: running instance of an image.
  • Registry: remote image store.
  • Tag: mutable human-readable reference such as v1.4.0.
  • Digest: immutable reference such as sha256:...; preferred for production deployments.

Orchestration concepts

  • Kubernetes: orchestrates containers using declarative resources.
  • GKE: Google-managed Kubernetes. Control plane is managed in both modes; Standard gives more node-pool and infrastructure control.
  • Helm: package manager and templating engine for Kubernetes manifests. A Helm package is a chart; an installed chart is a release.

Minimal Dockerfile

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN useradd --create-home appuser
USER appuser
EXPOSE 8080
CMD ["python", "app.py"]

Use a small trusted base image, pin dependencies, run as non-root, and keep the build context small.

Typical workload hierarchy

  • Deployment → manages replicated Pods and rolling updates.
  • Pod → smallest schedulable unit; normally one application container.
  • Service → stable virtual endpoint for Pods.
  • Ingress / Gateway → HTTP routing and load balancing.
  • ConfigMap → non-sensitive configuration.
  • Secret → sensitive data; not automatically equivalent to a cloud secret manager.

Build, tag, and run locally

docker build -t my-api:dev .
docker run --rm -p 8080:8080 my-api:dev
docker images
docker logs <container>
docker exec -it <container> sh

Prefer explicit version tags over latest; use .dockerignore to avoid copying credentials, caches, .git, and datasets.

Create a GKE cluster

Autopilot:

gcloud container clusters create-auto my-cluster \
  --location=us-central1

Standard:

gcloud container clusters create my-cluster \
  --location=us-central1 \
  --num-nodes=3

Use a regional cluster for higher control-plane availability. Validate supported versions and flags before production.

Artifact Registry image naming

LOCATION-docker.pkg.dev/<PROJECT_ID>/<REPOSITORY>/<IMAGE>:<TAG>

Example:

us-central1-docker.pkg.dev/acme-prod/apps/my-api:v1.4.0

Artifact Registry is the recommended GCP destination for Docker images; configure Docker authentication for the specific registry hostname.

Connect kubectl to GKE

gcloud container clusters get-credentials my-cluster \
  --location=us-central1

kubectl config current-context
kubectl get nodes
kubectl get namespaces

get-credentials updates your kubeconfig so kubectl can communicate with the cluster.

Push to Artifact Registry

gcloud artifacts repositories create apps \
  --repository-format=docker \
  --location=us-central1

gcloud auth configure-docker us-central1-docker.pkg.dev

docker build -t \
  us-central1-docker.pkg.dev/acme-prod/apps/my-api:v1.4.0 .
docker push \
  us-central1-docker.pkg.dev/acme-prod/apps/my-api:v1.4.0

Grant the GKE node or workload identity permission to pull private images.

Imperative deployment (quick test)

kubectl create deployment my-api \
  --image=us-central1-docker.pkg.dev/acme-prod/apps/my-api:v1.4.0
kubectl expose deployment my-api \
  --type=LoadBalancer --port=80 --target-port=8080
kubectl get deploy,pods,svc

Use version-controlled YAML or Helm for repeatable environments; imperative commands are best for experiments.

Multi-stage production build

FROM node:22 AS build
WORKDIR /src
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /src/dist /usr/share/nginx/html

The final image should contain only runtime assets — not compilers, package caches, source trees, or secrets.

Declarative Deployment skeleton

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-api
spec:
  replicas: 3
  selector:
    matchLabels: {app: my-api}
  template:
    metadata: {labels: {app: my-api}}
    spec:
      containers:
      - name: my-api
        image: REGION-docker.pkg.dev/PROJECT/REPO/my-api:v1.4.0
        ports: [{containerPort: 8080}]

The selector and Pod labels must match exactly.

Health and lifecycle inside the image

Implement separate endpoints when possible:

  • /livez: process is alive.
  • /readyz: able to receive traffic.
  • /startupz: slow startup completed.

Do not use a readiness probe to indicate liveness; a temporary dependency failure should usually remove a Pod from traffic, not restart it.

Probes, resources, graceful shutdown

resources:
  requests: {cpu: "250m", memory: "256Mi"}
  limits: {cpu: "1", memory: "512Mi"}
readinessProbe:
  httpGet: {path: /readyz, port: 8080}
livenessProbe:
  httpGet: {path: /livez, port: 8080}
startupProbe:
  httpGet: {path: /startupz, port: 8080}

Requests influence scheduling; limits cap usage. Missing or unrealistic requests produce poor scheduling and autoscaling behavior.

Reproducibility & supply-chain controls

  • Pin base images and dependencies where practical.
  • Scan images for vulnerabilities.
  • Generate and retain SBOMs.
  • Sign and verify images where supported.
  • Deploy by digest for strict immutability.
  • Never bake API keys into an image layer.
docker inspect my-api:v1.4.0

Container networking model

Inside a container, bind the server to 0.0.0.0, not only 127.0.0.1:

app.run(host="0.0.0.0", port=8080)

Container port declarations document intent but do not publish traffic by themselves.

Environment configuration

Use environment variables or mounted files for runtime configuration:

docker run --env-file .env my-api:v1.4.0

Do not commit .env files. Build-time arguments can leak through image history and should not carry secrets.

Service types

  • ClusterIP: internal-only virtual IP; default.
  • NodePort: exposes a port on nodes; usually an implementation detail.
  • LoadBalancer: provisions a cloud load balancer; useful for L4 traffic.
  • ExternalName: DNS alias, not a proxy.

For HTTP routing, prefer GKE Ingress or Gateway API rather than one public load balancer per microservice.

Docker Compose vs Kubernetes

Compose is excellent for local multi-container development:

services:
  api:
    build: .
    ports: ["8080:8080"]

Compose is not a replacement for GKE's scheduling, service discovery, autoscaling, rollout, identity, and cloud load-balancing.

ConfigMap and Secret usage

kubectl create configmap my-api-config \
  --from-literal=LOG_LEVEL=info
kubectl create secret generic my-api-secret \
  --from-literal=API_KEY='REDACTED'

For GCP services, prefer Secret Manager plus its integration. Restrict RBAC access and avoid exposing Secret values in logs or manifests.

Debug image failures

docker run --rm -it --entrypoint sh IMAGE
docker history IMAGE
docker inspect IMAGE

Common causes: wrong CPU architecture, missing shared libraries, incorrect working directory, wrong port, file permissions, or a process that exits immediately.

Namespace isolation & debug

kubectl create namespace staging
kubectl -n staging apply -f k8s/

kubectl describe pod <pod>
kubectl logs <pod> --previous
kubectl get events --sort-by=.lastTimestamp
kubectl top pods

Pending → scheduling/resource issues; ImagePullBackOff → image/auth/name problems; CrashLoopBackOff → repeated process failure. Namespaces need RBAC, NetworkPolicies, and quotas for real isolation.

Entrypoint and command

Exec-form commands receive signals correctly:

ENTRYPOINT ["./server"]
CMD ["--port", "8080"]

A shell-form entrypoint can prevent the app from receiving SIGTERM, delaying graceful termination.

Graceful termination

Configure application shutdown handling, a suitable terminationGracePeriodSeconds, and — if needed — a preStop hook. Ensure the app stops accepting new requests before exiting. Rolling updates require old and new versions to coexist safely.

Image pull policy

Use immutable tags or digests. Avoid latest — it makes rollback and auditability difficult.

image: .../my-api@sha256:<digest>

Private Artifact Registry access

GKE must be authorized to pull the image. Prefer least-privilege IAM and Google-managed identity mechanisms rather than long-lived registry passwords. Image streaming can reduce startup latency for eligible images.

Docker security baseline

  • Non-root USER.
  • Read-only filesystem where possible.
  • Drop Linux capabilities.
  • No privileged mode unless unavoidable.
  • Minimal packages.
  • No host socket mount in untrusted workloads.
  • Treat images as code and scan them continuously.

GKE identity baseline

Use Workload Identity Federation for GKE for Pods accessing Google Cloud APIs. Always enabled in Autopilot; enable it for Standard clusters. Grant IAM permissions to narrowly scoped Kubernetes ServiceAccounts rather than distributing static credentials.

Docker resource behavior

Local Docker limits are not automatically equivalent to Kubernetes resources. Test memory behavior explicitly, especially for Python, JVM, Node.js, and ML workloads. For GPU workloads, the image must include compatible user-space libraries and the cluster must provide compatible drivers/runtime support.

GKE Autopilot vs Standard

  • Autopilot: Google manages nodes, scaling, and many security/reliability defaults; generally the best starting point.
  • Standard: you control node pools, machine types, taints, custom node configuration, and specialized infrastructure.

Autopilot still supports customization through supported resource requests, scheduling controls, ComputeClasses, and workload configuration.

Local-to-cloud parity

Use the same image in local tests, CI, staging, and production. Keep configuration outside the image. Test with the same non-root user and similar CPU/memory assumptions.

Autoscaling layers

  • HPA: adjusts Pod replicas based on CPU, memory, or custom metrics.
  • VPA: recommends or adjusts requests; understand restart implications.
  • Cluster autoscaler: adds/removes nodes in Standard clusters.
  • Autopilot provisions underlying compute based on workload requirements.

Set realistic requests before trusting autoscaling.

Helm installation and repositories

helm version
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
helm search repo ingress-nginx

Helm can also install charts directly from OCI registries using the oci:// prefix; adding a classic chart repository is not required for OCI charts.

Helm lifecycle

helm upgrade --install my-api ./charts/my-api \
  --namespace staging --create-namespace \
  --values values-staging.yaml \
  --set image.tag=v1.4.0 \
  --wait --timeout 10m

helm list -A
helm status my-api -n staging
helm history my-api -n staging
helm rollback my-api 2 -n staging

upgrade --install is convenient for idempotent deployments; use explicit chart and image versions in CI.

Helm chart structure

my-api/
├── Chart.yaml
├── values.yaml
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   ├── serviceaccount.yaml
│   └── _helpers.tpl
└── charts/

Chart.yaml describes the chart; values.yaml provides defaults; templates/ renders Kubernetes manifests.

Helm validation before install

helm lint ./charts/my-api
helm template my-api ./charts/my-api \
  -f values-staging.yaml \
  --set image.tag=v1.4.0
helm diff upgrade my-api ./charts/my-api \
  -n staging -f values-staging.yaml

Render and review manifests in CI. Never assume a successful Helm command means the application is healthy.

Safe Helm values pattern

image:
  repository: REGION-docker.pkg.dev/PROJECT/REPO/my-api
  tag: v1.4.0
  pullPolicy: IfNotPresent
replicaCount: 3
service:
  type: ClusterIP
  port: 80
containerPort: 8080
resources:
  requests: {cpu: 250m, memory: 256Mi}
  limits: {cpu: "1", memory: 512Mi}

Values precedence

Lowest to highest, commonly:

  1. Chart defaults in values.yaml.
  2. One or more -f values files, in supplied order.
  3. --set or --set-string overrides.

Use --set-string for values that must remain strings. Avoid putting secrets in shell history or Git.

Container registry promotion

Promote the same immutable image digest through environments rather than rebuilding source separately for staging and production. A rebuild can produce a different artifact even when the source commit is unchanged.

Helm release promotion

Keep environment differences in values files:

helm upgrade --install my-api ./charts/my-api \
  -n prod --create-namespace \
  -f values-prod.yaml \
  --set image.digest=sha256:... \
  --atomic --wait --timeout 15m

--atomic rolls back on failure when supported; test hooks, migrations, and rollback behavior before depending on it.

CI pipeline outline

checkout → test → lint → build → scan → push → deploy

Use commit SHA or release version tags, capture the image digest, and pass that digest to deployment. Separate build credentials from runtime credentials.

Kubernetes CI/CD checks

  • helm lint.
  • helm template.
  • Kubernetes schema validation.
  • Policy checks for privileged containers, missing requests, public Services, and unpinned images.
  • Deploy to a disposable or staging namespace.
  • Wait for rollout and run smoke tests.
  • Promote only the verified digest.

Port mapping mental model

Docker:

host:8080 → container:8080

Kubernetes:

Service.port → Service.targetPort → containerPort

containerPort is descriptive; targetPort determines where the Service sends traffic.

GKE external traffic

For HTTP(S), GKE Ingress configures an Application Load Balancer from an Ingress and associated Service; Gateway API is the modern alternative for many routing designs. Use Cloud Armor for edge protection and IAP where identity-based application access is required.

Persistent data warning

Containers are ephemeral. Do not store production state only in the writable container layer. Use managed databases, object storage, or Kubernetes persistent volumes backed by suitable GCP storage.

Stateful workloads

Use StatefulSet only when stable identity or ordered storage is required. For many applications, Cloud SQL, Memorystore, Cloud Storage, or another managed service is operationally safer than self-hosting state in Pods. Back up data independently of cluster and Helm release state.

Logging and observability

Write application logs to stdout/stderr in structured JSON when possible. Include request IDs, trace IDs, severity, and useful context; never include tokens, passwords, or personal data unnecessarily.

Common Docker mistakes

  • Using latest in production.
  • Running as root unnecessarily.
  • Copying secrets into layers.
  • Installing build tools in the final image.
  • Binding only to localhost.
  • Ignoring signal handling.
  • Assuming local architecture matches GKE nodes.
  • Forgetting .dockerignore.

Common Kubernetes/Helm mistakes

  • Missing resource requests.
  • Selector/label mismatch.
  • Wrong targetPort.
  • Public LoadBalancer when internal access is enough.
  • Hard-coded credentials in values files.
  • No readiness probe.
  • No rollout timeout or rollback plan.
  • Treating Helm rollback as a database rollback.
  • Granting broad IAM or RBAC permissions.

Production image rule

Build once, test the exact artifact, scan it, push it, and deploy the resulting digest. Treat the image as a versioned release artifact rather than a temporary by-product of CI.

Production GKE rule

Declare everything necessary for recovery in version control — manifests/charts, values, and the pinned image digest — so environments can be reliably recreated and audited.

Build without a Docker daemon (Cloud Build)

# Build+push in-cloud, no local Docker needed
gcloud builds submit --tag \
  us-central1-docker.pkg.dev/PROJECT/apps/my-api:v1.4.0

Useful for CI runners lacking Docker; also enables Buildpacks (--pack).

Binary Authorization (supply-chain gate)

# Only allow attested/signed images to deploy to GKE
gcloud container binauthz policy import policy.yaml

Enforcement mechanism that pairs with the SBOM/signing controls — blocks unsigned/unattested images from deploying.

Native sidecars (K8s ≥ 1.29)

initContainers:
- name: proxy
  restartPolicy: Always   # makes it a sidecar
                          # with proper lifecycle

A native sidecar starts before app containers and is terminated after them, with correct startup/shutdown ordering.

Secret Manager → GKE via CSI driver

# Secrets Store CSI Driver mounts
# Secret Manager secrets as files
csi:
  driver: secrets-store.csi.k8s.io
  volumeAttributes: { secretProviderClass: "my-spc" }

The mechanism behind "prefer Secret Manager": mounts cloud-managed secrets as files instead of storing them in Kubernetes Secrets.

PodDisruptionBudget skeleton

apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 2
  selector: { matchLabels: { app: my-api } }

Keeps a minimum number of Pods available during voluntary disruptions (node drains, upgrades, autoscaling).

NetworkPolicy example

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
spec:
  podSelector: { matchLabels: { app: my-api } }
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: { matchLabels: { role: frontend } }

Provides the real network isolation that namespaces alone do not; only frontend Pods may reach my-api.

Cost & rightsizing

  • Autopilot bills per Pod resource request → requests directly drive cost.
  • Use Spot Pods for fault-tolerant batch:
nodeSelector:
  cloud.google.com/gke-spot: "true"

Right-size requests before scaling; over-requesting wastes money on Autopilot, under-requesting harms scheduling.

Cluster / version lifecycle

Autopilot always uses release channels — pick regular or stable. Plan for GKE auto-upgrades and Kubernetes deprecated-API removals (e.g., Endpoints). Test against upcoming versions before channels roll them out.
