Claude API Cheat Sheet

Practical reference extracted from Building with the Claude API. Verify model names, tool-version strings, and API behavior against current Anthropic documentation before production use.

1. Setup and first request

Install and configure

pip install anthropic python-dotenv

.env:

ANTHROPIC_API_KEY="your-api-key-here"
  • Add .env to .gitignore; never hard-code or commit API keys.
  • Initialize the client:
from dotenv import load_dotenv
from anthropic import Anthropic

load_dotenv()
client = Anthropic()
model = "claude-sonnet-4-0"

Minimal request

message = client.messages.create(
    model=model,
    max_tokens=1000,
    messages=[
        {"role": "user", "content": "Explain quantum computing in one sentence."}
    ],
)

text = message.content[0].text

Core parameters

ParameterPurpose
modelModel identifier to use.
max_tokensUpper safety limit for generated tokens; not a target length.

temperatureControls variability; use deliberately for the task.

2. Conversations and system prompts

Stateless API: manage history yourself

Claude does not retain conversation history between requests. For a multi-turn interaction:

  1. Append the user message.
  2. Send the complete history.
  3. Append Claude's full response as an assistant message.
  4. Append the next user message.
  5. Send the full history again.
def add_user_message(messages, text):
    messages.append({"role": "user", "content": text})

def add_assistant_message(messages, text):
    messages.append({"role": "assistant", "content": text})

def chat(messages, system=None, temperature=1.0, stop_sequences=None):
    params = {
        "model": model,
        "max_tokens": 1000,
        "messages": messages,
        "temperature": temperature,
    }
    if system:
        params["system"] = system
    if stop_sequences:
        params["stop_sequences"] = stop_sequences
    return client.messages.create(**params)

When a response contains tools or multiple content blocks, append the entire response.content, not only extracted text.

System prompts

Use system prompts to establish a stable role, tone, constraints, and workflow:

system = """
You are a patient math tutor. Do not immediately provide the final answer.
Guide the student step by step with hints and questions.
"""
response = chat(messages, system=system)

Only include system when it has a value; avoid sending system=None if unsupported by the API call.

Temperature guidance

RangeTypical use
0.0–0.3Factual answers, coding, extraction, moderation.
0.4–0.7Summaries, education, constrained problem solving.
0.8–1.0Brainstorming, creative writing, marketing, jokes.

Temperature changes probabilities; it does not guarantee a different output.

3. Streaming

Streaming improves perceived latency by delivering generated content incrementally.

Simplified text streaming

with client.messages.stream(
    model=model,
    max_tokens=1000,
    messages=messages,
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
    final_message = stream.get_final_message()

Use stream.get_final_message() when you need the complete response for storage or downstream processing.

Important events

  • message_start: message begins.
  • content_block_start: content block begins.
  • content_block_delta: generated content chunks; text is usually here.
  • content_block_stop: block ends.
  • message_delta: message metadata/final state.
  • message_stop: message ends.

4. Clean structured output

Claude may wrap JSON or code in Markdown and add commentary. For raw structured output, combine:

  1. A clear output-only instruction.
  2. Assistant-message prefilling.
  3. A stop sequence.
  4. Parsing and validation in application code.
import json

messages = [
    {"role": "user", "content": "Generate a short EventBridge rule as JSON."},
    {"role": "assistant", "content": "```json"},
]
response = chat(messages, stop_sequences=["```"])
obj = json.loads(response.content[0].text.strip())

This pattern also applies to Python, regex, CSV, lists, and other formats. Do not trust model output merely because it looks structured—parse and validate it.

5. Prompt engineering

High-value prompt structure

A robust prompt commonly contains:

  1. Direct action: start with Write, Create, Generate, Analyze, or Identify.
  2. Task and context: state what the model must accomplish and what information it should use.
  3. Output requirements: specify format, length, fields, tone, and exclusions.
  4. Process steps: for complex tasks, require a systematic workflow or checklist.
  5. Examples: show representative input/output pairs, especially failure cases.
  6. Delimiters: use XML-like tags around variable data and examples.

Weak: What should this person eat?

Better: Generate a one-day meal plan for an athlete that meets the athlete's dietary restrictions.

Be specific

Output guidelines should define:

  • Required sections or fields.
  • Exact format and length.
  • Required facts, calculations, or constraints.
  • Tone and audience.
  • Prohibited commentary or formatting.

For difficult problems, add process steps such as identifying assumptions, considering alternatives, checking constraints, and validating the final result.

XML-style delimiters

Use descriptive tags to separate instructions, data, code, and documentation:

<athlete_information>
Height: 188 cm
Weight: 82 kg
Goal: Build muscle
Restrictions: Vegetarian
</athlete_information>

Generate a meal plan using the athlete information above.

Useful tags include <user_data>, <sales_records>, <my_code>, <docs>, <sample_input>, and <ideal_output>.

One-shot and multi-shot examples

Examples are particularly valuable for:

  • Edge cases and sarcasm.
  • Exact JSON or code formats.
  • Desired tone and style.
  • Ambiguous inputs.

Use one example to establish a pattern; use multiple examples to cover distinct cases. Prefer high-scoring examples from evaluation runs, and explain why an ideal output is good.

6. Prompt evaluation

Evaluation loop

  1. Define the goal and success criteria.
  2. Write a baseline prompt.
  3. Build a representative dataset.
  4. Run every case through the prompt.
  5. Grade outputs with code, model, or human graders.
  6. Compute metrics and inspect failures.
  7. Change one prompt element at a time.
  8. Re-run and keep measurable improvements.

Do not rely on one or two manual tests; production users generate unexpected inputs.

Minimal evaluation architecture

def run_prompt(test_case):
    prompt = f"""
    Solve the following task:
    {test_case['task']}
    """
    response = chat([{"role": "user", "content": prompt}])
    return response.content[0].text

def run_eval(dataset):
    results = []
    for test_case in dataset:
        output = run_prompt(test_case)
        results.append({"test_case": test_case, "output": output})
    return results

Use small datasets, such as 2–3 cases, during development; expand for final validation. Limit concurrency initially to avoid rate limits.

Grader types

GraderBest forCaveat
Code graderParsing, syntax, length, required/forbidden strings, format.Limited semantic judgment.
Model graderHelpfulness, completeness, instruction following, safety, task fit.Can be variable or biased.
Human graderNuanced quality, relevance, depth, and overall judgment.Slow and expensive.

Define criteria before grading. For generated code, separate format, syntax, and task correctness.

Syntax validators

import ast, json, re

def validate_json(text):
    try:
        json.loads(text.strip())
        return 10
    except json.JSONDecodeError:
        return 0

def validate_python(text):
    try:
        ast.parse(text.strip())
        return 10
    except SyntaxError:
        return 0

def validate_regex(text):
    try:
        re.compile(text.strip())
        return 10
    except re.error:
        return 0

A simple combined score is:

score = (model_score + syntax_score) / 2

Adjust weights to match product priorities. Track averages, per-case scores, failure categories, and regressions—not just one headline score.

7. Tool use

What tools solve

Tools let Claude access current data or perform actions through your application. The standard loop is:

  1. Send the user request plus tool schemas.
  2. Claude returns a tool_use request.
  3. Your server validates arguments and executes the function.
  4. Your server sends a matching tool_result.
  5. Claude produces a final response or requests another tool.

Claude does not execute your Python functions automatically; your application owns execution, permissions, validation, and side effects.

Tool function best practices

  • Use descriptive function and parameter names.
  • Validate required and allowed inputs.
  • Return structured, serializable results.
  • Provide actionable error messages; Claude may correct and retry.
  • Enforce authorization, timeouts, rate limits, and idempotency for side effects.
  • Treat tool arguments as untrusted input.
from datetime import datetime

def get_current_datetime(date_format="%Y-%m-%d %H:%M:%S"):
    if not date_format:
        raise ValueError("date_format cannot be empty")
    return datetime.now().strftime(date_format)

Tool schema anatomy

get_current_datetime_schema = {
    "name": "get_current_datetime",
    "description": (
        "Return the current date and time in the requested format. "
        "Use this when an exact current timestamp is needed."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "date_format": {
                "type": "string",
                "description": "Python strftime format string.",
                "default": "%Y-%m-%d %H:%M:%S",
            }
        },
        "required": [],
    },
}

A schema has name, a detailed description, and input_schema containing types, properties, descriptions, defaults, and required fields.

Handling tool messages

A tool-enabled response can contain text and one or more tool_use blocks. Preserve the entire assistant content:

messages.append({"role": "assistant", "content": response.content})

For every tool request, return a matching result:

tool_result = {
    "type": "tool_result",
    "tool_use_id": tool_request.id,
    "content": json.dumps(tool_output),
    "is_error": False,
}
messages.append({"role": "user", "content": [tool_result]})

The tool_use_id must exactly match the originating request. If execution fails, send is_error: True with a useful error message.

Tool loop and routing

Continue until response.stop_reason != "tool_use":

def text_from_message(message):
    return "\n".join(
        block.text for block in message.content if block.type == "text"
    )

def run_tool(name, tool_input):
    if name == "get_current_datetime":
        return get_current_datetime(**tool_input)
    raise ValueError(f"Unknown tool: {name}")

def run_conversation(messages, tools):
    while True:
        response = chat(messages, tools=tools)
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return response

        results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            try:
                output = run_tool(block.name, block.input)
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": json.dumps(output),
                    "is_error": False,
                })
            except Exception as exc:
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": f"Error: {exc}",
                    "is_error": True,
                })
        messages.append({"role": "user", "content": results})

Claude may issue multiple tool calls in one response; process every tool_use block and return one corresponding result per ID.

8. Built-in tools and fine-grained calling

Web search

The built-in web search tool can retrieve current or specialized information. Enable it in the organization settings first, then provide the appropriate schema, for example:

web_search_schema = {
    "type": "web_search_20250305",
    "name": "web_search",
    "max_uses": 5,
    "allowed_domains": ["nih.gov"],  # optional restriction
}

Use max_uses to cap searches. Domain restrictions are useful for authoritative-source workflows. The response may contain search queries, result blocks, and citation blocks; render citations and sources in the UI.

Text editor tool

The text editor tool can view files/directories, inspect line ranges, replace text, create files, insert text, and undo edits. Claude supplies the tool knowledge, but your application must implement file operations and enforce sandboxing and permissions. The schema stub depends on the model/tool version, so consult current Anthropic documentation before deployment.

Fine-grained tool calling

Normal tool streaming may buffer until complete top-level JSON key/value pairs are validated. Fine-grained calling reduces buffering by disabling API-side JSON validation:

  • Enables more immediate argument chunks.
  • Requires robust handling of incomplete or invalid JSON.
  • Use only when responsiveness matters and your parser can recover safely.
try:
    parsed_args = json.loads(snapshot)
except json.JSONDecodeError:
    # Wait for more chunks or handle malformed input safely.
    pass

11. RAG & Agentic Search

What is RAG?

Retrieval Augmented Generation (RAG) means retrieving relevant document chunks, then generating answers with those chunks in the prompt. Use it when documents are too large or expensive to fit entirely in one prompt.

Why not stuff everything in the prompt?

  • Hard token limits; very long prompts degrade quality.
  • Higher cost and latency.
  • Claude becomes less effective with massive context.

RAG trade-off: more engineering upfront (chunking + search) for scalability, lower cost, and faster responses on large or multiple documents.

Core RAG workflow

  1. Preprocess: split documents into chunks.
  2. Index: store chunks in a searchable index (vector DB, BM25, hybrid).
  3. Query: embed/analyze the user question; retrieve top-k relevant chunks.
  4. Prompt: inject only the retrieved chunks and question into Claude.
  5. Answer: Claude responds using the provided context.

When to use RAG: very large documents, many documents, or when you must optimize cost and performance.

Chunking strategies

Pick a strategy based on the guarantees provided by the document.

Size-based (character/token) chunking

  • Split text into fixed-length pieces; add overlap to preserve context.
  • Pros: simple, works on any content (including code/PDFs).
  • Cons: can cut sentences or headers; may lose local context without overlap.
def chunk_by_char(text, chunk_size=150, chunk_overlap=20):
    chunks = []
    start_idx = 0
    while start_idx < len(text):
        end_idx = min(start_idx + chunk_size, len(text))
        chunk_text = text[start_idx:end_idx]
        chunks.append(chunk_text)
        start_idx = (
            end_idx - chunk_overlap if end_idx < len(text) else len(text)
        )
    return chunks

Structure-based chunking

  • Split by natural document structure (headers, sections).
  • Pros: high-quality, semantically coherent chunks.
  • Cons: requires well-structured inputs (for example, Markdown).
import re

def chunk_by_section(document_text):
    pattern = r"\n## "
    return re.split(pattern, document_text)

Sentence-based chunking

  • Split into sentences; group N sentences per chunk with optional overlap.
  • Pros: good middle ground; preserves sentence boundaries.
  • Cons: needs sentence splitting; chunk size varies.
def chunk_by_sentence(text, max_sentences_per_chunk=5, overlap_sentences=1):
    sentences = re.split(r"(?<=[.!?])\s+", text)
    chunks = []
    start_idx = 0
    while start_idx < len(sentences):
        end_idx = min(start_idx + max_sentences_per_chunk, len(sentences))
        current_chunk = sentences[start_idx:end_idx]
        chunks.append(" ".join(current_chunk))
        start_idx += max_sentences_per_chunk - overlap_sentences
        if start_idx < 0:
            start_idx = 0
    return chunks

Semantic-based chunking

  • Group sentences by semantic similarity (NLP/embeddings).
  • Pros: most relevant chunks.
  • Cons: computationally expensive; complex to implement.

Practical default: size-based chunking with overlap. It is reliable across arbitrary documents and will not break your pipeline.

Retrieval and ranking tips

  • Use hybrid retrieval (dense vector + keyword/BM25) to reduce misses from synonym and polysemy issues.
  • Retrieve top-k chunks (for example, 3-8) and consider re-ranking by a small model for precision.
  • Add metadata to chunks (source, section, page) to improve filtering and citations.
  • Watch for context gaps: a single chunk may omit necessary definitions; consider retrieving neighboring chunks or a small context window around hits.

Prompt pattern for RAG

Keep it tight and explicit:

You are an assistant that answers using only the provided context.
If the context doesn't contain the answer, say so.

<context>
{retrieved_chunks}
</context>

<question>
{user_question}
</question>

Answer concisely. Cite the section/source when possible.

Add instructions to avoid hallucination and to state uncertainty when context is insufficient.

Common pitfalls and fixes

  • Wrong domain results (for example, bugs in medical versus software content): improve chunk boundaries and use hybrid retrieval; add metadata filters.
  • Lost section context: include headers with each chunk or retrieve adjacent chunks.
  • Over-retrieval: too many chunks bloat prompts; tune k and re-rank.
  • Under-retrieval: increase k, improve embeddings, or add query rewriting.
  • Stale data: rebuild indexes when documents change; version your index.

Agentic search (tool-augmented RAG)

Extend RAG with tools so the agent can:

  • Search internal indexes or web sources.
  • Filter by metadata (date, domain, section).
  • Iterate: retrieve → reason → decide to fetch more → answer.

Pattern:

  1. User query → agent decides to call search(query, filters).
  2. Tool returns top results (snippets + metadata).
  3. Agent evaluates sufficiency; if insufficient, refines the query or fetches more.
  4. Final answer is synthesized from retrieved evidence; include citations.

Use this when a single static retrieval is not enough or when you need multi-source synthesis.

Quick checklist (production)

  • [ ] Choose a chunking strategy based on document structure guarantees.
  • [ ] Add overlap for size-based chunking to preserve context.
  • [ ] Store chunk metadata (source, section, page, timestamp).
  • [ ] Use hybrid retrieval + re-ranking; tune top-k.
  • [ ] Instruct the model to rely on provided context and cite sources.
  • [ ] Handle insufficient context explicitly.
  • [ ] Monitor retrieval quality (precision/recall) and answer faithfulness.
  • [ ] Re-index on document updates; version your index.

Text embeddings

  • Semantic search retrieves chunks based on meaning and context rather than exact keyword matches.
  • A text embedding is a numerical vector representing the semantic meaning of text.
  • An embedding model converts text into a list of floating-point numbers, commonly in the range [-1, 1].
  • Embedding dimensions are learned features; their individual meanings are generally not directly interpretable by humans.
  • Embeddings allow text to be compared mathematically.

VoyageAI example

Anthropic does not provide embedding generation in this workflow, so VoyageAI is used as the embedding provider.

pip install voyageai

.env:

VOYAGE_API_KEY="your_key_here"

Python:

from dotenv import load_dotenv
import voyageai

load_dotenv()

client = voyageai.Client()

def generate_embedding(
    text,
    model="voyage-3-large",
    input_type="query"
):
    result = client.embed(
        [text],
        model=model,
        input_type=input_type
    )
    return result.embeddings[0]
  • Embeddings can be generated individually or in batches.
  • The embedding API typically normalizes vectors to magnitude 1.0.
  • Use the appropriate input_type for queries versus documents when supported by the model.

Complete RAG pipeline

A basic RAG pipeline:

  1. Split source documents into logical chunks.
  2. Generate an embedding for every chunk.
  3. Store embeddings and original content in a vector database.
  4. Embed the user’s query using the same embedding model.
  5. Search for the most similar chunks.
  6. Insert the retrieved chunks into the LLM prompt.
  7. Generate an answer grounded in the retrieved context.

Preprocessing versus query time

  • Preprocessing: chunk documents, generate embeddings, and populate the vector database.
  • Query time: embed the user question, search the database, and construct the final prompt.

Important storage rule

Always store the original chunk text—or a reference to it—alongside its embedding. The embedding alone is not useful for constructing the final LLM prompt.

chunks = chunk_by_section(text)
embeddings = generate_embedding(chunks)

store = VectorIndex()

for embedding, chunk in zip(embeddings, chunks):
    store.add_vector(
        embedding,
        {"content": chunk}
    )

Query example:

user_embedding = generate_embedding(
    "What did the software engineering department do last year?"
)

results = store.search(user_embedding, 2)

for doc, distance in results:
    print(distance, doc["content"][:200])

Similarity metrics

Cosine similarity

Cosine similarity measures the angle between two vectors:

  • Range: -1 to 1.
  • Near 1: highly similar.
  • Near 0: weak or no directional relationship.
  • Near -1: opposite directions.

For normalized vectors, cosine similarity can be computed efficiently using the dot product.

Cosine distance

cosine_distance = 1 - cosine_similarity

Interpretation:

  • Near 0: highly similar.
  • Larger values: less similar.

Do not confuse ranking direction: similarity is better when higher; distance is better when lower.

BM25 lexical search

Semantic search can miss exact identifiers, codes, names, or technical phrases. BM25 provides lexical search based on exact term matching.

BM25 is especially useful for:

  • Incident IDs.
  • Product codes.
  • Error messages.
  • Legal or financial terminology.
  • Proper names.
  • Exact phrases.

BM25 process

  1. Tokenize the query.
  2. Count term frequency in documents.
  3. Give greater weight to rare terms.
  4. Rank documents containing the most important query terms.

Rare terms receive higher importance than common words.

chunks = chunk_by_section(text)

store = BM25Index()

for chunk in chunks:
    store.add_document({"content": chunk})

results = store.search(
    "What happened with INC-2023-Q4-011?",
    3
)

Semantic versus lexical search

Search typeStrengthLimitation
Semantic/vectorUnderstands meaning and conceptual similarityMay miss exact identifiers
Lexical/BM25Finds exact terms and rare phrasesDoes not understand meaning well
HybridCombines both strengthsRequires result fusion

Hybrid retrieval

A robust RAG system usually combines vector search and BM25 search.

Architecture

  • VectorIndex: retrieves conceptually similar chunks.
  • BM25Index: retrieves exact term matches.
  • Retriever: queries both indexes and merges their rankings.
  • All indexes should expose a consistent interface, such as:
    • add_document(document)
    • search(query, k)
class Retriever:
    def __init__(self, *indexes):
        if len(indexes) == 0:
            raise ValueError("At least one index must be provided")
        self._indexes = list(indexes)

    def add_document(self, document):
        for index in self._indexes:
            index.add_document(document)

This modular design makes indexes interchangeable, testable, and extensible.

Reciprocal Rank Fusion

Search systems often produce incompatible score scales, so merge rank positions instead of raw scores.

Formula

RRF(d) = Σ_i 1 / (k + rank_i(d))

Where:

  • d is a document or chunk.
  • rank_i(d) is its position in search result list i.
  • k is a smoothing constant, commonly 60.
  • Higher RRF scores indicate better combined rankings.

Example with k=1:

  • Section 2: ranks 1 and 2 → 1/(1+1) + 1/(1+2) = 0.833
  • Section 7: ranks 2 and 3 → 1/(1+2) + 1/(1+3) = 0.583
  • Section 6: ranks 3 and 1 → 1/(1+3) + 1/(1+1) = 0.750

Final ranking:

Section 2 > Section 6 > Section 7

A document that performs well across multiple retrieval methods is promoted.

Practical design principles

  • Use logical document sections as chunks when the document structure is meaningful.
  • Generate document embeddings in batches for efficiency.
  • Embed queries with the same embedding model used for the indexed content.
  • Preserve original text and metadata with every vector.
  • Use vector search for conceptual questions.
  • Use BM25 for exact terms and identifiers.
  • Prefer hybrid retrieval for production RAG systems.
  • Merge rankings with RRF rather than directly comparing incompatible scores.
  • Keep retrieval indexes behind a common interface.
  • Add new retrieval strategies—keyword, graph, or domain-specific indexes—by implementing the same interface.
  • Retrieve the top k chunks, then place them in a clearly delimited prompt context.

A useful mental model is:

Documents
  → chunks
  → embeddings + metadata
  → vector index

User query
  → query embedding
  → vector search
  → BM25 search
  → RRF fusion
  → retrieved context
  → LLM answer

12. Features of Claude

Extended thinking

  • Use Extended Thinking for complex reasoning when standard prompting, even after optimization, does not reach the required accuracy.
  • It returns a structured response containing a thinking block and a final answer block.
  • Benefits: better reasoning on difficult tasks, potentially higher accuracy, and greater visibility into the model's reasoning process.
  • Trade-offs: higher cost because thinking tokens are billed, increased latency, and more complex response parsing.
  • Important compatibility restrictions exist with features such as message pre-filling and temperature. Check Anthropic's compatibility documentation before combining features.
  • The thinking block includes a cryptographic signature to prevent modification or tampering.
  • Thinking may be returned as redacted thinking when internal safety systems flag its content. Preserve and pass the complete block back in subsequent requests to retain context.

Configuration pattern:

params["thinking"] = {
    "type": "enabled",
    "budget": thinking_budget
}
  • The minimum thinking budget is 1,024 tokens.
  • max_tokens must be greater than the thinking budget.

Recommended workflow:

  1. Test with standard prompting.
  2. Improve the prompt.
  3. Enable extended thinking only if accuracy remains insufficient.
  4. Test that your application handles both readable and redacted thinking blocks.

Image support

Claude can describe, compare, count, classify, and analyze images.

  • Limits: maximum 100 images across all messages in one request; maximum 5 MB per image.
  • One image can have a maximum dimension of 8,000 px; multiple images can have a maximum dimension of 2,000 px.
  • Images can be sent as Base64-encoded data or a URL.

Approximate image token cost: image tokens = (width × height) / 750

Send images using an image block alongside a text block:

{
    "type": "image",
    "source": {
        "type": "base64",
        "media_type": "image/png",
        "data": image_bytes
    }
}

Image prompting follows the same principles as text prompting:

  • Give explicit instructions and specify an analysis methodology.
  • Break complex tasks into steps and use one-shot or multi-shot examples.
  • Ask the model to verify its result using a second method.
  • For counting objects, request object-by-object identification followed by an independent recount.
  • For visual risk assessment, define what to identify, the measurements or categories, the scoring rubric, and the exact output format.

Reliable visual-analysis pattern

Analyze the image using these steps:

1. Identify the relevant objects or structures.
2. Examine each object according to the specified criteria.
3. Estimate or categorize the required measurements.
4. Verify the findings using an independent method.
5. Return one sentence per step and a final numerical rating.

PDF support

PDFs are sent as document blocks rather than image blocks.

{
    "type": "document",
    "source": {
        "type": "base64",
        "media_type": "application/pdf",
        "data": file_bytes
    }
}
  • When adapting image code for PDFs, use .pdf instead of .png, rename image_bytes to file_bytes, and set "type" to "document".
  • Claude can analyze text, images and charts, tables and relationships, and document structure and formatting.
  • Use PDFs for document summarization, extraction, visual analysis, table interpretation, and question answering.

Citations

Citations ground Claude's answers in the supplied source instead of leaving users with an unverifiable response.

For PDF citations, add a readable title and enable citations:

{
    "type": "document",
    "source": {
        "type": "base64",
        "media_type": "application/pdf",
        "data": file_bytes
    },
    "title": "earth.pdf",
    "citations": {
        "enabled": True
    }
}

Citation metadata can include cited_text, document_index, document_title, start_page_number, and end_page_number. For plain text documents, citations use character positions instead of page numbers.

Citations are especially useful when users must verify claims, documents are authoritative, transparency is important, or users need to inspect surrounding context.

Prompt caching

Prompt caching reuses preprocessing work from previous requests. It can make repeated requests faster and cheaper.

  • Best use cases: multiple questions about the same large document, iterative editing with stable source material, large system prompts, and reusable tool definitions.
  • Cache lifetime is one hour; caching is not automatic, so add explicit cache breakpoints.
  • A breakpoint caches all content up to and including that point. Follow-up requests use the cache only when that content is identical; even one changed character can invalidate it.
  • Cached content must contain at least 1,024 tokens, and you can use up to four cache breakpoints.
  • Processing order is Tools → System prompt → Messages.
  • Suitable targets include stable system prompts, tool schemas, reusable conversation history, and unchanged image or document blocks.
  • A breakpoint can span multiple messages and block types.

Use the expanded text-block format because shorthand strings do not support cache_control:

{
    "type": "text",
    "text": system,
    "cache_control": {
        "type": "ephemeral"
    }
}

To cache tool schemas, add the breakpoint to the final tool:

tools_clone = tools.copy()
last_tool = tools_clone[-1].copy()
last_tool["cache_control"] = {"type": "ephemeral"}
tools_clone[-1] = last_tool
params["tools"] = tools_clone

Usage indicators are cache_creation_input_tokens for tokens written to cache and cache_read_input_tokens for tokens retrieved. If only part of a request changes, Claude may read unchanged cached components while recreating changed components.

Files API and code execution

Files API

Upload files separately and receive a reusable file ID. Reference the file ID in later messages instead of embedding the file repeatedly as Base64.

  • Useful for reusing the same file and for large PDFs, images, or datasets.
  • It separates file management from inference requests.

Code execution

Claude can execute Python through a predefined server-side tool in an isolated Docker container.

  • The environment has no network access, can execute code multiple times in one conversation, and returns execution results for Claude to interpret.
  • Code execution is useful for data analysis, plotting, image processing, document transformation, mathematical modeling, and report generation.

Files API + code execution workflow

  1. Upload a file through the Files API.
  2. Include its file ID in a container_upload block.
  3. Ask Claude to analyze or transform it.
  4. Claude writes and executes Python code.
  5. Claude can create plots, reports, or other output files.
  6. Download generated files using the file IDs returned in code_execution_output blocks.
{
    "type": "container_upload",
    "file_id": file_metadata.id
}

Enable code execution with:

tools=[
    {
        "type": "code_execution_20250522",
        "name": "code_execution"
    }
]

Code-execution responses may contain normal text blocks, server tool-use blocks containing code, and code-execution result blocks. Always parse structured responses defensively, including thinking, citation, tool-use, redacted, and generated-file blocks.

Practical rules

  • Prefer standard prompting first; use extended thinking only when needed.
  • For vision tasks, provide a repeatable methodology rather than a vague question.
  • For document-heavy applications, combine PDF support, citations, and prompt caching.
  • Cache stable tools and system prompts to reduce latency and cost.
  • Use the Files API for files that will be referenced repeatedly.
  • Use code execution for computational or file-generation tasks, while designing around its lack of network access.

13. Model Context Protocol (MCP)

MCP in one sentence

Model Context Protocol (MCP) is a standardized communication layer that lets AI applications connect to external data and functionality through reusable MCP servers, avoiding the need to implement and maintain every integration manually.

Core idea

  • MCP client: Connects an application to MCP servers.
  • MCP server: Exposes tools, resources, and prompts for an external service.
  • AI model: Uses the capabilities exposed by the MCP server.
  • External service: GitHub, databases, files, APIs, Jira, Slack, browsers, and other systems.

MCP is not the same as model tool use:

  • Tool use describes the model requesting an action.
  • MCP defines how tools, resources, and prompts are packaged, discovered, and executed by external servers.

MCP architecture

User
  ↓
Application / AI agent
  ↓
MCP client
  ↓
MCP server
  ↓
External service, database, filesystem, or API

An MCP server acts as a reusable wrapper around an external service. For example, a GitHub MCP server can expose operations for repositories, issues, pull requests, and projects without the application author having to implement every GitHub API schema and function.

Who creates MCP servers?

  • Service providers can publish official servers.
  • Companies can build internal servers for proprietary systems.
  • Individual developers can create custom servers.
  • Applications generally implement either an MCP client or an MCP server, not both. Implementing both is mainly useful for learning or building a complete platform.

Communication

MCP is transport-agnostic. Clients and servers may communicate through:

  • Standard input/output (stdio), often when both run on the same machine.
  • HTTP.
  • WebSockets.
  • Other supported network transports.

Important message pairs

MessagePurpose
ListToolsRequest / ListToolsResultDiscover the tools provided by a server.
CallToolRequest / CallToolResultExecute a tool with arguments and return its result.
ReadResourceRequestRequest data identified by a resource URI.
Prompt listing/getting operationsDiscover prompts and retrieve an interpolated prompt.

Typical tool-call flow

  1. The user submits a request.
  2. The application asks the MCP client for available tools.
  3. The client sends ListToolsRequest to the MCP server.
  4. The application sends the user request and tool definitions to the model.
  5. The model selects a tool and returns a tool-use request.
  6. The application asks the MCP client to execute the tool.
  7. The client sends CallToolRequest to the MCP server.
  8. The MCP server calls the external service.
  9. The result returns through the MCP server and client.
  10. The application sends the result back to the model.
  11. The model generates the final response.

Tools, resources, and prompts

Tools: perform actions

Use tools for operations that do something, such as:

  • Editing a document.
  • Creating a ticket.
  • Sending a message.
  • Querying or modifying a database.
  • Calling an external API.
  • Running a browser action.

Tools are defined with @mcp.tool.

from mcp.server.fastmcp import FastMCP
from pydantic import Field

mcp = FastMCP("DocumentMCP", log_level="ERROR")

@mcp.tool(
    name="read_doc_contents",
    description="Read the contents of a document and return it as a string."
)
def read_document(
    doc_id: str = Field(description="ID of the document to read")
) -> str:
    if doc_id not in docs:
        raise ValueError(f"Document with ID {doc_id} not found")
    return docs[doc_id]

The Python SDK automatically provides:

  • JSON Schema generation from type hints.
  • Parameter validation through Pydantic.
  • Better IDE support and type safety.
  • Less boilerplate.
  • Readable, maintainable tool definitions.

Resources: expose data

Use resources when the client needs to retrieve data rather than perform an action. They are conceptually similar to GET endpoints.

Examples:

  • Listing available files.
  • Reading document contents.
  • Exposing configuration.
  • Providing database or application context.
  • Supplying data directly to a model prompt.

Resources are defined with @mcp.resource.

Direct resource

A static URI always refers to the same type of data:

@mcp.resource(
    "docs://documents",
    mime_type="application/json"
)
def list_docs() -> list[str]:
    return list(docs.keys())

Templated resource

A URI contains parameters:

@mcp.resource(
    "docs://documents/{doc_id}",
    mime_type="text/plain"
)
def fetch_doc(doc_id: str) -> str:
    if doc_id not in docs:
        raise ValueError(f"Document with ID {doc_id} not found")
    return docs[doc_id]

The SDK extracts {doc_id} from the URI and passes it to the function.

Tools versus resources

FeatureToolsResources
Main purposePerform an actionRetrieve data
Typical analogyPOST, PUT, or commandGET
ExampleEdit a documentRead a document
Model interactionModel explicitly requests executionClient retrieves and includes data as context
Decorator@mcp.tool@mcp.resource

Resources can reduce unnecessary tool calls because data can be fetched and inserted directly into the prompt.

MIME types

The mime_type tells the client how to interpret the returned data:

  • application/json — Structured JSON.
  • text/plain — Plain text.
  • Other valid MIME types — HTML, CSV, XML, images, binary files, and so on.

The SDK handles serialization automatically.

Prompts

Prompts are reusable, predefined instructions exposed by an MCP server. They are useful when the server author has domain-specific instructions that are more reliable than an ad hoc user prompt.

Good MCP prompts should be:

  • Specific.
  • Well-tested.
  • Relevant to the server's purpose.
  • Clear about expected output.
  • Designed to work with available tools and resources.
  • Parameterized when user-specific values are required.
from mcp.server.fastmcp import base

@mcp.prompt(
    name="format",
    description="Rewrite a document in Markdown format."
)
def format_document(
    doc_id: str = Field(description="ID of the document to format")
) -> list[base.Message]:
    prompt = f"""
    Reformat the document identified by {doc_id} using Markdown.
    Add headers, bullet points, and tables where appropriate.
    Use the edit_document tool to apply the changes.
    """
    return [base.UserMessage(prompt)]

Prompt lifecycle

  1. The client calls list_prompts().
  2. The user selects a prompt.
  3. The client calls get_prompt(prompt_name, arguments).
  4. The server interpolates the arguments.
  5. The client receives a list of messages.
  6. The messages are sent to the model.
async def list_prompts(self) -> list[types.Prompt]:
    result = await self.session().list_prompts()
    return result.prompts

async def get_prompt(
    self,
    prompt_name: str,
    args: dict[str, str]
):
    result = await self.session().get_prompt(prompt_name, args)
    return result.messages

MCP client implementation

An MCP client usually wraps the SDK's client session to simplify communication and handle cleanup correctly.

Core methods:

async def list_tools(self) -> list[types.Tool]:
    result = await self.session().list_tools()
    return result.tools

async def call_tool(
    self,
    tool_name: str,
    tool_input: dict
) -> types.CallToolResult | None:
    return await self.session().call_tool(tool_name, tool_input)

Resource access

import json
from pydantic import AnyUrl

async def read_resource(self, uri: str):
    result = await self.session().read_resource(AnyUrl(uri))
    resource = result.contents[0]

    if isinstance(resource, types.TextResourceContents):
        if resource.mimeType == "application/json":
            return json.loads(resource.text)
        return resource.text

The client should:

  • Reuse a persistent session where appropriate.
  • Close sessions and subprocesses reliably.
  • Parse responses according to their MIME type.
  • Handle missing resources and server errors.
  • Keep transport concerns separate from application logic.

Testing and debugging

Start the inspector

Or:

uv run mcp dev mcp_server.py

The inspector normally starts a local development server, commonly using port 6277.

  1. Start the MCP Inspector.

  3. Click Connect.
  4. Navigate to Tools, Resources, or Prompts.
  5. List available items.
  6. Enter required parameters.
  7. Run the operation.

For state-changing operations, test a read operation afterward to confirm that the expected change was applied.

Minimal project setup

A typical educational MCP project may contain:

MCP design checklist

Server design

  • Define a clear server purpose.
  • Expose narrow, composable tools.
  • Use descriptive tool names and descriptions.
  • Use type hints and Pydantic Field descriptions.
  • Validate identifiers and user inputs.
  • Return structured data when appropriate.
  • Use accurate MIME types for resources.
  • Raise descriptive errors.
  • Avoid exposing unnecessary permissions.
  • Test every operation with the inspector.

Client design

  • Encapsulate the SDK session.
  • Implement tool discovery.
  • Implement tool execution.
  • Implement resource reading when needed.
  • Implement prompt discovery and retrieval when needed.
  • Parse content based on MIME type.
  • Clean up sessions and subprocesses.
  • Keep application logic independent from transport details.

Agent integration

  • Give the model only the tools it needs.
  • Use resources for context retrieval.
  • Use tools for actions.
  • Use prompts for repeatable, domain-specific workflows.
  • Require confirmation before destructive or external side-effecting operations.
  • Log tool calls and failures.
  • Treat external tool output as untrusted input.
  • Apply authentication, authorization, validation, rate limits, and least privilege.

Key distinctions to remember

MCP server = packages and exposes capabilities
MCP client = discovers and invokes capabilities
Tool = performs an action
Resource = provides data
Prompt = provides reusable instructions
Model = chooses how to use the exposed capabilities
Application = orchestrates the complete interaction

The central advantage of MCP is integration reuse: developers can connect AI applications to external systems through standardized servers instead of repeatedly writing and maintaining custom schemas, API clients, and execution code.

15. AI Workflows and Agents

Core distinction

Workflow: A predefined sequence of LLM calls and processing steps for a known problem. Use it when you can describe the solution flow in advance.

Agent: Give the model a goal, tools, and environment access; the model decides which steps and tools to use. Use it when the task, parameters, or solution path are unpredictable.

AspectWorkflowAgent
ExecutionPredetermined sequenceDynamically planned
Best forWell-defined, repeatable tasksNovel or variable tasks
ReliabilityGenerally higherGenerally lower
TestingEasier to instrument and evaluateMore difficult to predict and evaluate
FlexibilityLimitedHigh
Planning effortMore upfront designLess rigid upfront design
Production guidancePreferred when sufficientUse only when flexibility is genuinely required

Engineering rule: Prefer workflows whenever they can reliably solve the problem. Use agents only when the exact process cannot be predetermined.

Common workflow patterns

These patterns help structure repeated AI tasks when the problem can be split into reliable steps, explicit evaluation criteria, or specialized pipelines.

Evaluator–optimizer

Use this pattern when an output can be generated, evaluated against criteria, and iteratively improved.

Input
  ↓
Producer → Output
  ↓
Grader/evaluator
  ├─ Accept → Finish
  └─ Reject → Feedback → Producer → Repeat

Components:

  • Producer: Generates or modifies the output.
  • Grader: Checks the output against explicit quality criteria.
  • Feedback loop: Sends detected problems back to the producer.
  • Iteration: Continues until the result meets the acceptance criteria.

Example: image → object description → CAD model → rendering → comparison with original → correction if necessary.

Use it for generated code, CAD models, documents, media, reports, and other outputs with verifiable quality requirements.

Parallelization workflow

Use parallelization when a complex decision can be divided into independent evaluations.

Input
 ├─ Specialized evaluator A
 ├─ Specialized evaluator B
 ├─ Specialized evaluator C
 └─ Specialized evaluator N
          ↓
      Aggregator
          ↓
    Final decision

Implementation:

  1. Split the task into focused sub-tasks.
  2. Run independent sub-tasks concurrently.
  3. Give each sub-task specialized prompts, tools, or criteria.
  4. Aggregate the results.
  5. Use a final LLM call or deterministic function to produce the decision.

Example: evaluate an object independently for metal, polymer, ceramic, composite, elastomer, and wood suitability, then aggregate the analyses into one recommendation.

Benefits:

  • Reduces cognitive load on the model.
  • Enables deeper analysis of each dimension.
  • Allows prompts to be optimized independently.
  • Makes adding new evaluation categories easier.
  • Improves consistency and scalability.

Use it when sub-tasks are genuinely independent. Do not parallelize steps that depend on the output of another step.

Chaining workflow

Use chaining when a task consists of sequential, dependent steps or when one large prompt produces unreliable results.

Task input
  ↓
Step 1 → Step 2 → Optional code/tool processing → Step 3

Key characteristics:

  • Sub-tasks execute sequentially.
  • Each step receives the previous step’s output.
  • Non-LLM processing can occur between calls.
  • Each model call focuses on one responsibility.

Example:

Find trending topics
  → Select a topic
  → Research it
  → Write a video script
  → Generate the video
  → Publish it

Constraint-revision pattern

Instead of asking the model to create content and satisfy many constraints simultaneously:

  1. Generate the initial draft.
  2. Send the draft to a second call.
  3. Ask the second call to check and correct specific violations.

Example revision instructions:

Revise the article below:
1. Remove statements identifying the author as an AI.
2. Remove all emojis.
3. Replace awkward or clichéd writing with professional technical language.

Use chaining when:

  • The task has multiple requirements.
  • A long prompt causes the model to ignore constraints.
  • Outputs must be validated or transformed between steps.
  • Steps cannot run independently.
  • You want each interaction to remain focused and manageable.

Routing workflow

Use routing when different input categories require different prompts, tools, or processing pipelines.

User input
    ↓
Router/classifier
    ↓
Category
 ├─ Educational pipeline
 ├─ Entertainment pipeline
 ├─ Review pipeline
 └─ Other specialized pipeline

Process:

  1. Define mutually useful categories.
  2. Ask the model or a classifier to assign the input to one category.
  3. Select the category-specific prompt or pipeline.
  4. Process the request using only that specialized path.

Example categories for video generation:

  • Educational.
  • Entertainment.
  • Comedy.
  • Personal vlog.
  • Reviews.
  • Storytelling.

Example classifier prompt:

Categorize the topic into exactly one category:

<topic>Python functions</topic>

<categories>
- Educational
- Entertainment
- Comedy
- Personal vlog
- Reviews
- Storytelling
</categories>

The category determines the specialized generation prompt. For example, an educational pipeline should emphasize clarity, definitions, digestible explanations, relatable examples, and useful questions.

Use routing when:

  • Requests differ significantly in style or domain.
  • Categories can be defined clearly.
  • Classification is reliable enough.
  • Specialized processing improves quality more than the routing step increases latency and cost.

Agent design and operations

Once the model needs to act on the environment, the design focus shifts to tool composition, inspection, and safe operation.

Agent tool design

Agents become powerful when they can combine simple, reusable tools in different sequences.

Prefer abstract, composable tools over tools tied to one narrow task.

Good general-purpose tools:

  • bash: Execute commands.
  • read: Read files.
  • write: Create files.
  • edit: Modify files.
  • glob: Find files by pattern.
  • grep: Search file contents.

Avoid exposing only highly specialized tools such as refactor_code or install_dependencies. General tools let the agent adapt to scenarios that were not explicitly anticipated.

Example tool set for a media agent:

  • bash with FFmpeg access.
  • generate_image.
  • text_to_speech.
  • post_media.

A composable tool set can support both a fixed process and adaptive behavior, such as generating a sample, requesting user approval, and then continuing with full production.

Environment inspection

An agent must be able to observe the effects of its actions. Without inspection, it is effectively executing commands blindly.

Design every action around this question:

How will the agent know whether the action worked?

Inspection techniques:

  • Read files before modifying them.
  • Capture screenshots after UI interactions.
  • Inspect API responses for expected values.
  • Validate generated files and content.
  • Compare outputs against the original requirements.
  • Run tests or verification commands after changes.

Safe file modification

Read current file
  ↓
Understand structure and dependencies
  ↓
Edit file
  ↓
Run validation/tests
  ↓
Inspect result

Reading before writing helps preserve existing behavior and prevents changes from being made without understanding the current structure.

Media verification example

For a video-generation agent:

  • Use Whisper or whisper.cpp to create timestamped captions.
  • Use FFmpeg to extract screenshots at regular intervals.
  • Check that dialogue, captions, and visual elements appear at the correct times.
  • Compare the result with the original requirements.
  • Correct and re-render when necessary.

Environment inspection improves:

  • Progress tracking.
  • Error detection and recovery.
  • Quality assurance.
  • Adaptive decision-making.

Selection checklist

Choose a workflow when:

  • The steps are known in advance.
  • The task is repeatable.
  • Reliability and predictable behavior matter.
  • You need straightforward testing and evaluation.
  • The product UX already constrains the available actions.

Choose an agent when:

  • The task path cannot be predicted.
  • Users may provide varied or novel requests.
  • The model must decide which tools to use.
  • The agent may need to ask for missing information.
  • Creative tool combinations are valuable.

Choose a parallel workflow when independent analyses can run concurrently.

Choose a chaining workflow when steps depend on previous outputs.

Choose an evaluator–optimizer when results can be judged against explicit criteria and improved iteratively.

Choose a routing workflow when inputs fall into categories requiring distinct processing.

Production design principles

  • Decompose complex tasks rather than relying on one massive prompt.
  • Keep each LLM call focused on one responsibility.
  • Make evaluation criteria explicit.
  • Use deterministic code for transformations and validation when possible.
  • Parallelize only independent work.
  • Chain dependent work.
  • Route requests to specialized pipelines.
  • Give agents tools that are abstract, observable, and composable.
  • Add inspection after every important action.
  • Validate outputs before declaring the task complete.
  • Prefer the simplest architecture that meets the requirements.
  • Start with a workflow; upgrade to an agent only when the workflow is insufficient.
